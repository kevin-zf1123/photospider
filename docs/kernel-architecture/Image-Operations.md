# Image operations

## Scope and current availability

Structured `Result` is the public semantic, input, output, publication, and ownership contract for built-in image operations. Current built-in image operations include `image.exposure_gain`, `image.opacity`, `image.brush_circle`, `image.mask`, `image.source_over`, `image.mix`, `image.gaussian_blur`, `image.downsample_box`, `mask.downsample_box`, `image.split_horizontal`, `image.stmap`, and the two local inpainting operations. All use the Result operation API. A Result schema declares typed image slots backed by typed tensor storage, which can use a private `PlanarImage` backing or immutable affine `CpuStorage`; it may also declare primitive fields. Ordinary non-image numeric `Value` remains valid.

The standalone planar callback table, planar image executor, and planar workflow binding were removed. Legacy planar C entry points v1-v3 are rejected. The built-in operations listed above execute through Result image slots. Other image families remain outside this migration; the table below distinguishes their current source and runtime state from the implemented Result path.

## Native Metal operations for RGBA images

The shared helper in `plugins/ops/rgba32f/image_gpu.h` submits `image.metal` through the Result native GPU service. CMake reads the shader and generates an embedded header; the old standalone C DSO is not part of the product surface. Native Metal is registered for `image.exposure_gain`, `image.opacity`, `image.gaussian_blur`, `image.mask`, `image.source_over`, `image.downsample_box`, `mask.downsample_box` and `image.brush_circle`. `image.mix` and `image.split_horizontal` have CPU implementations only. The eight Metal implementations passed real-dispatch validation in `test_builtin_result_images`; installed-library consumers `installed_builtin_result_images` and `installed_builtin_result_images_native` also pass (2/2), with 241 native dispatches including the 205-tile regression.

`tests/integration/test_metal_images.cpp` rejects 40 invalid image/coverage sample bindings and 26 invalid schema variants in each of CPU and native modes. Its native producer exercises owner alignment: with a 17-byte owner at offset 1, the producer performs one native dispatch and opacity then falls back to CPU without an opacity dispatch. With a 16-byte owner at offset 4 and channel origin 1, `byte_address` normalizes the view and the producer and opacity each perform one native dispatch. Both alignment cases report zero transfers. The four output samples remain readable after the execution context retires. CPU/native local checks and installed consumers `installed_image_domain` and `installed_image_domain_native` pass 2/2 in each environment.

RGBA operands use a `photospider.image` Result with one spatial Float32 HWC tensor named `pixels` and exactly two batch axes for frame and layer. Coverage operands use the same schema with one spatial Float32 HW tensor and the same batch axes. RGB samples may be finite signed/HDR values. RGBA semantics are linear and premultiplied: alpha must be finite and lie in [0,1], and zero alpha requires zero RGB. Coverage samples are finite and lie in [0,1]. Every frame/layer image is processed separately, and multi-image operations require matching batch extents.

Image Gaussian requires Int64 `radius` in [1,64] and Float64 `sigma` in [0.1,64]. Preparation computes and normalizes its Gaussian weights in Float64 using `exp`. CPU execution multiplies and accumulates taps in increasing order in Float64, rounds the horizontal pass once to Float32, then rounds the vertical pass once to Float32. Metal converts prepared weights to Float32 and uses compensated Float32 sums in its shader. The validated comparison bound is `abs(gpu - cpu) <= 1e-6 + 1e-5 * abs(cpu)`; this is not a CPU/GPU bitwise-equality contract. Both paths clamp spatial taps at image edges and request the necessary halo. Gaussian also treats Empty demand statelessly, with no source observations; a bounded small ROI can execute when the complete batch/sample cardinality overflows but the requested window remains representable.

GPU implementations may return `BackendUnavailable` for finite inputs outside their conservative native arithmetic domain. The operation traits permit CPU fallback for the eight operations with both implementations; the execution conditions and poll-time retry restrictions are described in [Compiler and Local Execution](Compiler-and-Execution.md). Other failures do not trigger fallback.

## Native alpha Result operations

The installed `photospider/format/alpha.hpp` appends FMT-04A/B and FMT-05A
nodes to ordinary workflows. Their nine native keys use Result ABI 2; FMT-05B/C
remain authoring compositions over existing extraction, literal-like fill,
mapped assembly and metadata assignment keys. These are generic single-tensor
operations, not special `photospider.image` slots. They preserve batch prefixes,
use cell-relative axes, and enforce full sample rank at most 8 and count at most
2^40. Inputs must contain one tensor and no fields; Float32/Float64 same-dtype
arithmetic is used, while extraction/removal and component copies retain the
seven supported raw-bit dtypes.

For FMT-04 semantic operations, participating color and consumed alpha samples
carry Data and Validation support; pass-through-only samples are copied without
extra sample validation. Raw association has arithmetic Data without semantic-
domain Validation. FMT-05A requests selected source colors as Data and
Validation, adds Validation-only support from the new alpha source for those
colors, and requests Data plus Validation for the published alpha channel. All
connected inputs receive Descriptor support; these operations use no Control.

FMT-04 associate/unassociate always materialize and expose no layout parameter.
Among the native alpha operations, only FMT-05A Set accepts a layout policy. A generic Set view requires the full
declared map to prove one `CpuStorage` owner and one affine relation; spatial Set
views are limited to internal identity. Set `auto` materializes only on physical
`ViewUnavailable`. Materialization publishes transactionally under Root budgets
and cancellation; Empty observations retain no run payload state. These FMT
operations do not add a GPU backend.

All current built-in `02-format-color` source families have Result CPU operations or helpers that lower to registered operations. FMT-01, FMT-02/03, FMT-04/05A alpha, FMT-06 numeric conversion, FMT-08, FMT-09 transfer, FMT-10 RGB basis, literal-like fill and scalar literal use Result operation ABI 2. The public headers `photospider/format/channel.hpp`, `channel_assembly.hpp`, `channel_editing.hpp`, `alpha.hpp`, `metadata.hpp`, `transfer.hpp` and `rgb_basis.hpp` and `model_conversion.hpp` are installed individually. FMT-05B/C are executable compositions of existing Result operations; FMT-04/05A and FMT-09/10 have native keys. Other production operations may remain registered while their structural-image Value contracts remain outside the Result image path. Registry presence alone does not establish Result image support.

## Built-in Result image operations

`image.exposure_gain`, `image.opacity`, `image.brush_circle`, `image.mask`, `image.source_over`, `image.mix`, `image.gaussian_blur`, `image.downsample_box`, `mask.downsample_box`, and `image.split_horizontal` accept structured `Result` inputs and publish structured `Result` outputs. Image slots use schema `photospider.image` version 1, with one tensor named `pixels` and no fields. Each slot declares exactly two batch axes for frame and layer and a spatial layout. RGBA algorithms require a Float32 HWC tensor with four channels and canonical linear premultiplied RGBA semantics; coverage inputs use a Float32 HW tensor with coverage semantics. Multi-image operations require matching frame/layer counts and spatial extents.

Local Navier-Stokes inpainting uses the same Result API and typed image schema. Its image and coverage inputs have matching frame/layer batches and spatial dimensions. It validates the complete `[N,L,H,W,4]` image and `[N,L,H,W]` mask domains, then publishes one complete image Result while preserving the accepted image schema and semantic facets. The profile requires canonical linear-sRGB premultiplied RGBA with opaque alpha, plus canonical coverage; it permits the declared scene or display reference. It does not accept CMYK or ICC ColorArray inputs and does not infer image meaning for untyped numeric tensors. The result can feed other typed image operations.

The image tensor's descriptor axes are cell axes. A coordinate such as `{frame, layer, y, x, channel}` addresses one RGBA sample, while `{frame, layer, y, x}` addresses one coverage sample. The HWC channel axis is logically one axis; `PlanarImage` may store its planes separately. Frame and layer remain batch axes and are preserved by these operations.

`image.exposure_gain` multiplies RGB by a control in `[0, 16]` and preserves alpha. `image.opacity` scales all four premultiplied RGBA channels with a control in `[0, 1]`. `image.brush_circle` takes seven controls after the image in order `x`, `y`, `radius`, `red`, `green`, `blue`, `alpha`; it paints pixel centers inside the circle, requires a positive normal Float32 radius, and bounds alpha to `[0, 1]`.

`image.mask` multiplies premultiplied RGBA by a coverage image. `image.source_over` takes foreground then background. `image.mix` takes two RGBA images followed by a coverage image used as the interpolation factor. `image.downsample_box` and `mask.downsample_box` require integer `factor` in `[1, 16]`, average each box, clip partial edge boxes, and use ceiling division for output height and width. `image.split_horizontal` requires `split_x` strictly inside the input width and publishes `full`, `left`, and `right` by copying HWC tensor samples. It accepts all seven supported tensor dtypes without requiring RGBA semantics, preserves the input tensor schema, and checks the complete bytes for each sample. Integration coverage checks UInt8, UInt16, and Float64 samples and publication when the split output exceeds its temporary workspace. The downsample tests also cover a factor-16 boundary near `UINT64_MAX`.

Each scalar control is a Result with one unbatched Float32 tensor whose sample shape is `{1}`. The tensor key may be any valid key because the input contract selects the sole tensor member. The sample can use an unaligned singleton stride, including `INT64_MIN`; the callback reads it through the Result tensor interface. Exposure, opacity, brush radius, and brush alpha bounds are validated on the control input. Out-of-range or non-finite direct bindings fail with `InvalidArgument` before output publication, including when the requested image footprint is Empty; invalid values produced by an upstream callback fail with `OperationFailed` during execution.

The scheduler requests the complete scalar sample for dependency validation, so a scalar value or validation change can dirty every output pixel that depends on it. Image inputs use the operation's mapped spatial support; for example, box downsampling requests the source box for each output region. An Empty output footprint does not request image samples. These behaviors describe the current built-in implementation. Native Metal support is limited to the eight operations listed in the RGBA Metal section above; the remaining operations in this table do not acquire GPU support from these contracts.

## Result image contract

A typed image slot carries a descriptor for one frame/layer, a planar physical layout, semantic facets, and a bounded number of frame/layer samples. Its logical coordinates are `{frame, layer, descriptor axes...}`; frame and layer are separate axes, not color channels. A Result can mix typed image slots and primitive fields under one schema. Do not encode image bytes as `ResultFieldSpec` records.

The compiler resolves the selected named output and its input projection. The Result continuation requests only declared inputs; a callback can read Control samples and then request the Data image support selected by those values. The published relation records both. Dirty transpose uses that same relation, so consumed controls can select new support without treating unrelated inputs as dependencies. `Exact`, `Conservative`, and `Unknown` keep their declared proof meaning.

The Result owner retains schema, certified descriptor facts, backing, relations, and consumed input owners. Admission uses the execution root for work, stages, I/O, relation/maps, payload, and owners. A failed publication is sticky. Cancellation and stale execution retire active callbacks before releasing their phase state. See [Structured Results and image slots](Global-Results.md), [Dependency Data](Dependency-Data.md), and [Tensor Storage and Region Access](../kernel-specs/Tensor-Storage-and-Region-Access.md).

## Public executable paths and limits

[`examples/image_vertical`](../../examples/image_vertical/README.md) compiles a two-node exposure/opacity graph over 5D RGBA Results and checks a one-pixel output against an independent binary-fraction oracle. [`examples/regional_image_vertical`](../../examples/regional_image_vertical/README.md) adds a direct two-dimensional Gaussian oracle, full-versus-ROI comparison, physical tile layouts, source-window checks, and a large zero-stride source fixture. Both examples bind source Results and execute under one `ResourceBudget` root; the publication observer reports completion of the requested Result output, not legacy tile streaming. The local `example_image_vertical` and `example_regional_image_vertical` tests pass; their installed-package consumer tests `installed_image_vertical` and `installed_regional_image_vertical` also pass. The regional affine-source fixture observed a 2328-byte peak Payload requirement and returned `ResourceExhausted` at 2327 bytes; this is not an RSS bound.

[`examples/s3_image_workflow`](../../examples/s3_image_workflow/README.md) adds application-level brush edits, slider coalescing, preview/export arbitration, and Result-cache checks. Its kernel plans use a 4-by-4 physical tile geometry, while the coordinator issues twenty separate 4-by-4 Result requests for export. A brush stamp rounds its bounding ROI outward to the tile grid and may span several physical tiles; the immutable edit adopts zero-copy identity row views of up to four columns while retaining source owners. This does not mean that one atomic full-domain kernel request is split by the application, nor does it reproduce the old Value tile stream. The full-resolution scene uses Gaussian radius 2 and sigma 1.0; its factor-4 proxy graph is used by the shared S3/S4 preview coordinator and uses radius 1 and sigma 0.25. The `preview` and `cache` scenarios use CPU execution. Both local tests and both installed consumer tests pass. The validated preview run applies nine stamps, requests twenty export regions and twenty-seven preview regions, and rejects three stale or invalid publications. The cache run reports zero blur polls after a gain edit and twelve blur polls for the local patch.

[`examples/s4_gpu_workflow`](../../examples/s4_gpu_workflow/README.md) runs the image graph and eight operations through direct public CPU or native Metal execution, with explicit whole, tiled, and ROI resident-chain layouts. The resident-chain Gaussian uses radius 2 and sigma 1.0; the separate all-operations Gaussian case uses radius 2 and sigma 1.25, while factor-four proxy downsampling is used by the shared S3/S4 preview coordinator. Its CPU oracle and native Metal dispatch checks are reported separately. `--explain` reports planned operations, selected backends, tensor full sample shapes, and the terminal output region; runtime Result needs determine input windows. Metal resident-chain, all-operation, cache, preview/export, and fallback scenarios require an available device when invoked with `--require-native`; CPU fallback is not evidence of Metal execution. The S4 Root uses a 16 MiB Payload limit, an 8 MiB Result cache limit, and 262144 dependency-cache metadata units; the default is 65536 units. The S4 local scenario and layout CTests pass 12/12; the five installed CPU and five installed Metal scenario tests pass 10/10. The validated native resident-chain reports five dispatches, three uploads and no fallback; all-operations reports 36 dispatches and no fallback. The cache-edits run observes zero work on a warm request, reuses blur after a gain change, and reports twelve blur polls for a local patch. Preview/export reports 219 image dispatches, excluding brush-stamp execution. These are fixture resource limits and execution checks, not RSS bounds or performance guarantees.

[`examples/unified_result_workflow`](../../examples/unified_result_workflow/README.md) remains a small public workflow using test/example-only minimal operations. It selects an image Result output and a numeric output, requests image regions, and exercises a dynamic support change. These examples cover only the listed paths; they do not add other built-in image operations. Ordinary numeric Values and non-image structured Results remain available.

## FMT-11 model conversion

FMT-11 A-R and T register 57 CPU keys across strict, Apple Silicon and x86-64 profiles. The installed authoring helpers append one key and return a `values` output containing one tensor; S lowers to `mask.threshold_channel_<profile>` and adds no color key. Inputs contain one Float32 or Float64 tensor and no fields. Full sample rank is at most 8; sample counts follow Result schema representability and execution resource limits. Axes are cell-relative and exclude the batch prefix.

Selected semantic samples request Data and Validation; raw T validates its two-level selector; raw S and bypass samples request Data; constant R output needs only Descriptor. Empty requests are stateless. Q supports generic and spatial view when the full requested mapping has a valid physical view. Other members materialize and reject forced view, including bypass-only requests. Outputs retain schema id, tensor key and batches while updating the selected model description and setting `atomic_trailing_axes` to zero. Six focused checks and the `installed_model_conversion`, `installed_model_result` and `installed_alpha_model_interop` installed consumers pass. These are generic tensor operations, not typed image-slot operations.
