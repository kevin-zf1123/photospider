# Structured Results and tensor slots

## Scope & Ownership

`ResultRef` is the semantic, publication, ownership, and input/output path for structured tensor data and image data. A Result contains typed tensor slots, packed primitive fields, or both. A tensor slot may carry image semantics and use internal planar typed backing; this does not create a separate image result path. `Value` is backing storage, not a workflow or operation input/output form.

Current package version is 0.32.0, WorkflowDocument schema is 5, and OperationTraits version is 24. The Result C operation header owns the operation-plugin interface under ABI 2, including its element types, parameters, facets, capability flags, and callback statuses; the former base operation C table has been removed. Native GPU services are declared separately under ABI 1. These version numbers describe independent contracts. The C++ operation interface uses `start_result` and `ResultContinuation`; consumers must rebuild against package 0.32.0. Result output records now include view-policy flags and an optional payload bound, so the nested C record layout has changed while the ABI remains 2. C modules must rebuild against the current exact-sized declaration; no prefix shim is provided. Package 0.32.0 defines the current Result-only C++ API contract. Migration of retained operations, examples, and integration consumers remains incomplete; the version number alone does not establish their validation.

The compiler copies immutable schema into the plan. The execution coordinator owns producer state and schedules callbacks and I/O. A `ResultRef` owns its schema, monotone descriptor facts, certified backing, dependency evidence, and source-association metadata. Copies of a reference share this ownership. An external reference or read window keeps required backing alive after the execution context ends. Association metadata identifies consumed inputs; it does not own their payloads.

```cpp
struct ResultTensorLayout final {
  bool spatial = false;
  ImagePlaneOrder order = ImagePlaneOrder::Tiled;
  std::uint32_t height_axis = 0, width_axis = 1;
  std::optional<std::uint32_t> channel_axis = 2;
  std::uint64_t row_pitch_bytes = 0;
  std::vector<ImageComponentGroup> groups;
};

struct ResultTensorSpec final {
  ResourceLease metadata_owner;
  ResourceString key;
  ResourceVector<std::uint64_t> batch_axes;
  std::uint32_t atomic_trailing_axes = 0;
  ValueDescriptor descriptor;
  ResultTensorLayout layout;
  std::vector<ValueFacet> facets;
};

struct SchemaTemplate final {
  ResourceString id;
  std::uint32_t version = 1;
  PublishPolicy publication = PublishPolicy::CompleteBundle;
  ResourceVector<ResultFieldSpec> fields;
  ResourceVector<ResultTensorSpec> tensors;
  ResourceVector<ResultExtent> domain;
  ResourceVector<ResultFacet> metadata;
};

struct WorkflowInputDeclaration final {
  std::uint64_t id;
  std::string name;
  std::shared_ptr<const SchemaTemplate> result_schema;
};

struct ExecutionBinding final {
  std::string name;
  ResultRef result;
};
```

The excerpt omits default member values and unrelated declarations. A workflow input with `result_schema` binds an owning `ResultRef`; execution returns named Result outputs in `ExecutionResult::results`. Tensor sample coordinates concatenate `batch_axes` with the descriptor's cell axes. There is no separate image output map.

Complete structured execution may compute a non-security `result_digest` over named Result outputs in `ExecutionResult::results`: canonical schemas, field row counts and bytes, and certified tensor coverage and sample bytes in logical order. It excludes object identity, source association, and physical layout; it is not authentication. Fragment execution leaves this digest empty. `ExecutionOptions::maximum_result_digest_samples` defaults to 65,536 and sets the combined admission limit for field elements and certified tensor samples; zero disables digesting. Before scanning, the coordinator also checks per-field row-window limits, remaining Run-work, and tensor coverage-count representability. If the complete digest does not fit these estimates, it omits the digest and continues with the execution result. For example, a large certified broadcast view need not be traversed once per logical sample solely to create a digest. After scan admission, digest reads use bounded windows and consume Run-work; cancellation, stale state, Root/resource, or read failures during that scan remain execution failures. The coordinator rechecks cancellation and stale state before returning success.

## Data Layout & Memory

`SchemaTemplate` has at most 16 combined field and tensor slots, up to eight domain axes, and bounded semantic metadata. A `ResultFieldSpec` describes a primitive element type, a row-count rule, and a record shape of rank zero through seven with positive extents. Row counts can be fixed, input-derived, tied to earlier field rows, or discovered at runtime. Fields are packed primitive records and remain separate from tensor sample bytes.

`ResultTensorSpec` describes a typed tensor member. Its cell descriptor has rank 1..8 with positive extents; `batch_axes` adds a positive-extent prefix, and the combined sample rank is at most eight. `atomic_trailing_axes` closes that many trailing cell axes into one indivisible observation. Schema validation does not impose a dense allocation or a representable full-domain element product. `ResultTensorLayout` records optional spatial layout, physical plane order, row pitch, and channel groups; storage order and pitch do not change semantic schema identity. A spatial layout maps height, width, and optional channel axes within the cell descriptor, independently of the batch prefix.

Tensor facets can impose additional sample rules. The semantic Image facet requires height and width on cell axes 0 and 1; the ColorArray facet closes its declared channel tuple. A tensor-description facet can describe another layout such as CHW. Layout groups alone do not require peer channels or alpha samples.

Sample authorization preserves tuple contracts for both the legacy semantic image facet and a validated `ColorArray` facet on a tensor slot. For a rank-3 semantic image cell, a spatial request closes over its complete channel tuple, including alpha when alpha is a channel. For `ColorArray`, the closure includes every channel in the declared tuple. Tensor-description facets and structural layout groups do not add peer-channel or alpha demand. A typed tensor without either tuple facet follows its sample coordinates and gains no inferred peer closure. Logical tuple completeness is independent of whether channel bytes are interleaved; planar storage may keep channels in separate planes.

`ResultBuilder` assigns an object id at construction, before runtime counts are known. The semantic key includes canonical schema and a length-framed execution scope. The scope binds the operation contract, parameters, ordered inputs, and captured query. Physical page size, file offsets, descriptor revision, tile dimensions, and resource limits do not change semantic identity. `ResultRef::capture()` snapshots the certified descriptor, field/tensor relations, descriptor basis, and dependency bundle at one revision. The host actor publishes only this captured view, so observers cannot see a prefix from a later revision paired with earlier evidence. `ResultRef::read_tensor()` requires that descriptor and reads only certified samples. `ResultTensorInput` carries the explicit tensor Need, slot, descriptor, and authorized sample set into a callback; the phase is borrowed for one poll, while its owning capabilities follow their own lifetime rules.

For each Result successfully supplied to an actor, the host keeps a Root-accounted historical fact keyed by input port and ObjectId, with the descriptor revision. This history identifies consumed sources but retains no payload and grants no read permission. `ResultObjectInputs` separately keeps the current owning ResultRef per input port across polls for the object-Need protocol; the host clears that map when the actor completes or retires. Stored `ResultTensorInput` capabilities own their ResultRef and captured descriptor, and acquired read windows own the backing authorized by that Need. A physical tensor view independently retains its source Results, schemas, selected resources, and backing.

For compiled structured CPU Whole operations with `preserve_output_views`, the coordinator prepares each payload-authorized Tensor Need after validating it and before the next computation poll. For each authorized box, it first proves an affine view over compatible source backing. If that mapping is unavailable, Auto may collect the authorized samples into immutable Root-owned private backing retained by the `ResultTensorInput`; `requires_input_views` instead returns `ViewUnavailable` before the computation callback. Auto does not turn work, cancellation, or resource failures into collection. Copies of the capability share the prepared backing and its Root metadata lease. The private `Value` is only backing: workflow inputs and outputs remain Results, and a published view retains the source Result identity, association, and resources. Direct Result phases do not automatically fulfill Needs or prepare these views. C Result output flags expose the same policies; the compiled CPU Whole coordinator performs the view preparation, while direct C callback entry does not synthesize it. This preparation path does not extend to joint or GPU view execution.

The coordinator prepares boxes independently. If a later `ResultTensorInput::acquire()` spans boxes that have no common affine mapping, it returns the original authorized compound window without copying. A completed-result cache replay validates the saved Need and its facts without repeating physical view preparation; a cache miss follows the ordinary callback Need path and prepares the view before computation.

The dependency records retain the full evidence separately from the small source-history index. `bind_result` binds tensor shapes, field counts, and descriptor domains; `record_object` imports source coverage and relations; `append_relation` records each output observation's support; and `capture_bundle` captures the resulting dependency graph. The host binds that bundle to the published Result before `ResultRef::capture()` freezes descriptor and dependency facts at one revision. Actor completion or retirement clears its transient input-history map; it does not erase the recorded dependency evidence. When execution builds an `ExecutionResult`, it snapshots the current evidence graph. The snapshot is independent of later actor progress and is admitted under Root capacity; insufficient capacity returns a resource failure.

Before publication, the host builds the ordered association from the actor's `(input port, ObjectId)` facts. `ResultRef::retain_association()` checks that IDs are nonzero, do not name the output itself, and preserve every previously claimed ID. It compares through a temporary sorted copy, leaving the stored port/ObjectId order unchanged and preserving repeated ObjectIds supplied through different ports. Membership checks charge Root work and observe cancellation; a failed check leaves the existing association unchanged. There is no fixed 1024-entry association limit: Root metadata capacity and Run-work admission bound the list.

Dynamic row counts belong to structured fields. When a callback consumes a `ResultObjectNeed`, the runtime binds the Field domain to the captured Result's certified row count before field access. Imported dependency bundles retain the largest observed Field domain: `bind_result` raises the recorded row extent, and `append_relation` compares the actual certified prefix domains from the old and incoming output footprints. A nonempty footprint's domain is its declared extent; an Empty footprint certifies zero rows, even when its shape `{1}` is only a placeholder. The function lifts both footprints to their maximum row domain and unions certified coverage. It selects the relation and descriptor from the longer certified prefix, with the incoming record selected on a tie. This choice uses the actual certified domains, not `ResultRelation::coverage()`, which can include support for rows that are not yet certified. Importing a shorter captured prefix does not shrink the recorded domain. This historical maximum does not extend a captured descriptor's authorization; reads remain limited to samples certified by that descriptor. A zero-row Result is valid and has no field payload page; its descriptor relation can still record count, basis, or validation support. Internal tensor backing requires nonzero extents and rejects the structural image facet. An Empty Footprint represents no requested samples in a nonzero logical domain; it does not create a zero-extent tensor.

## Scheduling & Publication

Each selected named output has its own resolved output contract and captured query. `ResultProgramQuery::tensor_outputs` contains the requested footprint for `tensor_slot`, and `output_index` identifies the selected output. An absent tensor footprint requests the full slot domain. The query, output index, static parameters, and tensor slot participate in producer identity; tile height, tile width, and page size are physical choices. Ordinary execution runs every non-side-effect-free operation as a mandatory root, including operations without a named output. Fragment and atom execution do so only for nonempty queries; completely empty queries skip unrelated effect roots. Within a Run, the internal actor identity for an effectful tensor output uses slot zero and full coverage, allowing later requests to reuse the actor. This does not authorize other tensor slots; their Needs and publication coverage remain checked. Effectful work is not shared or cached across Runs. Failure or cancellation of a mandatory root fails the Run.

Result C ABI operation definitions can declare a fixed input prefix and one repeated trailing group. `input_count` and `inputs` describe only the prefix; `repeated_input` supplies the prototype constraint applied to each actual trailing input during metadata resolution and `start`/`poll` query validation. A nonzero `repeated_maximum` enables the group and requires `1 <= repeated_minimum <= repeated_maximum`, with the prefix plus maximum no greater than 1,024 inputs. When disabled, all repeated fields are zero or null. `repeated_match` is 0 or 1: value 1 requires every repeated tensor to match the first repeated tensor's dtype and complete logical `sample_shape()`; value 0 requires a pure metadata resolver for the expanded input list. The C++ registry keeps the unexpanded template and resolves the actual input count during preparation. This declaration constrains metadata only; the operation still requests a Tensor Need for every actual input it reads.

The operation starts one host-owned `ResultContinuation`. Each poll returns a bounded `ResultProgramNeed` or a `ResultPublication`. A Need can contain Result-object, tensor, or I/O requests. Tensor needs identify input index, slot, logical samples, and roles. The coordinator validates the need against the Result input schema and published coverage, then supplies a capability-limited `ResultTensorInput`. A callback can first request Control samples, inspect them on the next poll, and then request the Data tensor support those values select. The returned `ResultRelation` records both support stages.

A native GPU callback can call `ResultProgramPhase::acquire_native_atlas(input, slot)` for a payload-authorized tensor Need. It returns an immutable `FragmentAtlas` containing exactly that Need's coverage; the operation still decides how to dispatch and publish. Calls for the same port and slot within one poll reuse one atlas. CPU access, a missing Need, or a Descriptor-only Need produces sticky `InvalidArgument` and does not widen authorization. An Empty payload Need returns a valid atlas with a one-byte inert payload and a two-slot empty directory, without reading source samples or dispatching native work. Root-backed payload and directory storage is separate from operation workspace, and the atlas owns those buffers without retaining the source Result or read windows. A caller-held shared atlas can remain alive after the poll, source, and execution context end.

Native GPU input transport reuses raw physical backing within a Run only while a weak proof still identifies the same live CPU storage and the complete view key matches. An optional byte-bounded context cache can reuse uploads across Runs by device instance/build and logical input bits, Region, dtype and shape; it excludes Result facets and resources, then rebinds a hit to current metadata and association. Cache hashing consumes the coordinator shared cache-work budget, and optional-work exhaustion skips the cache path. Capacity reclamation first clears retransmittable Run-local entries, then evicts retained context entries. `host_access_count` records actual CPU exposure of live native-backed storage, including Whole prepared reads, once per storage in a callback scope; metadata inspection, native-address acquisition, view forwarding and hashing do not count. Native GPU service failures are latched when the service call returns. A later `consume_work` exhaustion or callback status cannot replace that earlier service error; if work exhaustion occurs first, a later service error does not replace it.

Result atlas packing accepts either a current `ValueFragments` view or a `ResultTensorInput` capability. The Result overload reads through Need-authorized owning windows, so signed and broadcast strides, fragmented coverage, and batch-prefixed spatial tensors are handled without converting the Result to Value semantics. `preparation_work()` and `materialization_work()` report generic geometry and packing units. Result preparation precharges its generic work through `FootprintLimits::consume_work`; Result materialization additionally precharges window acquisition and read-bound work through that callback. `materialization_work()` is not the complete Result-overload charge.

The structured GPU block cache admits a native entry only after the compute callback records actual native dispatch work. A callback that returns a block state without dispatch does not seed a reusable native entry; a later request must compute again. The current control Need still contributes dependency evidence on a cache hit.

### Cross-output block-state sharing

Pure deterministic Atomic Result-v2 operations may opt into `share_blocks_across_outputs`. Registration rejects regional-atomic outputs and static dependency pieces. The C Result ABI 2 exposes the same opt-in as `PS_RESULT_FLAG_SHARE_BLOCKS_ACROSS_OUTPUTS_V2` (flag bit 5).

The shared namespace includes the operation and all resolved output contracts, backend, execution mode, static parameters, and actual input metadata. Each block key also includes its kind, range, mode, incoming state schema/coverage/content, and the currently supplied tensor metadata, coverage, and bytes. The selected output index and output-specific metadata are not appended independently. A computation shared by different outputs must therefore be output-independent or encode the distinction in its state or mode. Public output Results, their associations and dependency evidence, checkpoints, and completed-result caches remain output-scoped and independent. The C opt-in uses an existing operation flag and does not change the Result table layout.

Retention is optional and charged to cache work and Root limits. If lookup or retention is unavailable, the callback computes the block normally. A cache hit returns a fresh state without importing prior source association or evidence; the current output still completes its own Needs and records its own evidence. The flag does not deduplicate concurrent producers or guarantee one computation per Run. `examples/numeric_workflow/ordering.cpp::block_contracts` exercises the public Result-v2 phase API with a two-output dependency-v2 probe; sort and quantile remain Whole operations and do not use this facility.

The C bridge has a separate two-output fixture in `tests/fixtures/result_block_fixture.c`, exercised by `test_result_c_block` and the imported-package `installed_result_c_block` consumer. Both `value` and `control` execute the same six-step floating sum over a Float64 Result, but request different roles. With retention enabled, the first output computes six block transitions and the second reuses those states without importing the first output's Data evidence. Editing the first source sample reuses the three unaffected states and recomputes the three affected states. With retention disabled, both outputs compute their own transitions. Each publication retains its current source association and role-specific dirty mapping.

For a GPU Result attempt, the coordinator can retry on CPU only when the operation supports CPU and explicitly allows fallback. Start retry requires deterministic and side-effect-free traits plus clear cancellation, currentness, operation failure, and host-service checks. Poll retry additionally requires deterministic and side-effect-free traits, a retry-safe attempt, no published output, mandatory I/O, checkpoint or block callback, field I/O, native dispatch, cancellation, stale plan, or active stop. The reported status must be an unqualified `BackendUnavailable` (`reason=None`, origin unspecified or backend, scope unspecified or group). The host separately records a retry veto for later typed resource, protocol, callback, observer, or other nonretryable failures without replacing the first reported status. A retry retires the GPU continuation and its read capabilities and starts a CPU attempt with fresh failure owners; Root work and stage accounting remain charged. In the Result C ABI, both `api.start` and `api.poll` are invoked from `State::poll` and use the same poll-phase fallback gate. Other errors are terminal. The Result C ABI uses `PS_RESULT_FLAG_CPU_FALLBACK_V2` for this opt-in and requires both CPU and GPU capability flags. Ordinary C callback outcomes use the integer codes defined by `ps_result_status_v2`, distinct from typed Atom failure codes; poll yield and view-unavailable results follow their service contracts, while native GPU services use separate GPU status codes. Once a tensor, view, field, or Result has been successfully published, a callback return of `BackendUnavailable` becomes `OperationFailed`; `begin_result` alone does not count as publication. Root work and stage accounting are not refunded, and fallback-tainted results bypass optional caches. The registered `core.gpu_fallback_probe` exercises the startup case: it rejects GPU startup, then maps the requested tensor footprint on CPU; because startup failed before input access, that retry performs no upload or native dispatch. Diagnostics retain the rejected GPU start and CPU attempt and report CPU as the selected backend. `test_result_plugin.cpp::impure_start_fallback` checks that an impure GPU startup returning `BackendUnavailable` is not retried on CPU; this verifies startup eligibility, not native dispatch computation. The Result C plugin behavior entry points in `test_result_plugin.cpp` also cover opt-in and no-fallback operations, invalid/unsupported backend selection, `BackendUnavailable` returned by either the C `api.start` or `api.poll` callback, ordinary and unknown callback results, cancellation, begin-only attempts, publication-before-failure, sticky invalid service calls, a native dispatch before failure, and per-attempt start/destroy accounting. Direct `start_result` tests also verify that invalid reads followed by `BackendUnavailable` or cancellation preserve the sticky `InvalidArgument`; the native-dispatch case verifies that no CPU attempt starts after native work. They check that safe fallback retries stay outside the completed-result cache and that an invalid publication context does not poison a later valid publication; these are coverage locations, not a pass claim.

The structured C++ Result runner snapshots the dependency-record state before an eligible GPU attempt. The snapshot preserves exact typed Field, Tensor, and Descriptor records and relations, domains, imported identities, and immutable payload-free evidence owners. The new table wrapper and identity lease are Root-accounted; copying mutable metadata consumes Root capacity and mandatory Run work. Successful Need and checkpoint facts remain available across polls without copying sample payload into the snapshot. When a retry-safe attempt returns `BackendUnavailable` before native dispatch or publication, the runner discards that attempt's local continuation and capabilities, restores the snapshot, reimports any still-required peer evidence, and restarts the same query on CPU. Reimport binds the producer's own domain before merging records, so a restored field prefix can grow on retry. Records created only by the rejected attempt do not leak into the CPU result, while previously completed output evidence remains available. A completed Whole ancestor is imported from its local Result bundle when the retry needs it, avoiding a second computation. This is an exact Result-record transaction; it is distinct from the coverage-only checkpoint used by the older dependency-session path.

The C++ `tests/fixtures/operation_fixture.cpp` now exports 16 Result ABI 2 operations: its prior 15 operation keys plus `fixture.bad_bytes`. `test_plugin_registry.cpp` exercises Result workflow binding/readback, direct public start validation, and dynamic output metadata: the resolver copies the input facet into the inferred output, then the poll callback reads the sample and multiplies it by `scale`. The `fixture.bad_facet` case gives the metadata sink a zero-version facet and verifies rejection; `fixture.bad_bytes` supplies a 9-byte payload for an 8-byte tensor and expects `TypeMismatch`. Fallback modes 5 and 7 attempt to publish through tensor slot 99 and expect `InvalidArgument`. Ownership checks cover owner-allocation failure, plugin destruction, and native-library close accounting. `test_execution.cpp` covers opt-in GPU fallback and Result callback outcomes, duplicate publication, cancellation, and fallback accounting. A native-only invocation is registered separately and skips with code 77 when no GPU lane is available. Duplicate tests distinguish a valid repeated publication (`OperationFailed`) from an invalid first service call whose `InvalidArgument` remains sticky after a later valid attempt; actual host cancellation can override the former, while callback-returned `Cancelled` cannot. The Result C ABI has no legacy callback error-string channel: tests observe typed status, timing, and invocation counts, while numeric diagnostics use the separate `report_numeric` service. C++ operation execution uses the staged Result-v2 contract. The Result ABI 2 C table is the only C operation-plugin interface; there is no Base C plugin table.

Pure, deterministic Result programs can use the C++ `ResultProgramPhase::checkpoint_publish` and `checkpoint_before` callbacks to retain continuation state. Eligibility also requires the complete selected-input producer closure to be pure and deterministic. If an included producer is not shareable, lookup misses and publication declines normally. A published checkpoint owns a sealed Result state and a witness of successful Needs: input port, target, slot, roles, footprint, consumed ObjectIds and revisions, and dependency bundles for producer inputs. Scalar Needs are included. For an object Need, the witness records the descriptor and certified coverage for all fields and tensors.

Checkpoint lookup is scoped by operation template, frozen execution snapshot, and selected tensor slot. It does not include the requested output footprint, so demand changes can reuse state; the template still captures the selected output and its static contract. `checkpoint_before(phase, before)` returns the greatest published sequence in that phase not greater than `before`. Restoring a checkpoint rebinds its historical domains and dependency obligations and imports producer evidence. A successful restore also refreshes the current poll's `association` with the restored input history; references or iterators to its previous elements may be invalidated, while the borrowed vector remains valid until poll returns. It does not populate the current phase's `results` or `tensors`, recreate read windows, or grant Need authorization. The callback must request current input access again.

The context directory holds weak references to checkpoint scopes, while an active execution holds its scope strongly. Each scope retains at most 64 entries and is bounded by Root metadata and work admission. The runtime charges optional checkpoint work before constructing lookup keys, traversing producer closures, or copying Need history and metadata. Capturing producer dependency bundles also charges the full dependency traversal and copied evidence. Zero or insufficient optional cache fuel can skip lookup or decline publication; it does not consume unadmitted witness data. A copied `ResultCheckpoint` owns its state and witness even after the index or context is cleared. Optional cache, metadata, or capacity exhaustion can make lookup miss or publication decline without invalidating a successful operation; cancellation, protocol failures, and admitted Run-work failures remain errors. The C Result ABI exposes `checkpoint_before`, `checkpoint_read`, and `checkpoint_publish` through poll-scoped opaque handles and sealed generic state Results; see the [C checkpoint services](Dependency-Data.md#c-checkpoint-services) contract.

The completed Result cache reuses sealed Result outputs across frozen execution identities, including generations, when their consumed source content is unchanged. A retained entry contains the completed Result, its transitive dependency bundle, the typed source observations, and the original successful Result Need sequence with the ready facts observed after each Need. The cache key includes the operation template, selected output, tensor slot, backend, and exact requested tensor footprint `Q`; candidates therefore require the same `Q`. For each candidate, the runtime hashes current input bytes over recorded Field and Tensor supports, and hashes descriptor facts and schema for Descriptor supports. Target, slot, roles, and footprint are part of that proof; Data, Control, Validation, and Descriptor roles remain distinct. It then replays each saved Result Need against the current bindings and requires the ready facts to match before accepting the candidate. Unobserved input bytes do not affect the proof.

A cache hit creates a Result with a new ObjectId and the current execution scope. It carries the current ordered input association and the cached Result's sealed descriptor, relations, and tensor backing. The cache entry retains the physical backing owners it references; rebinding does not make the old Result wrapper or old execution scope the identity of the new output. Current upstream Results are replayed through the ordinary dependency recorder, so the published execution evidence reflects the current bindings. Repeated requests that share the same producer within one frozen execution continue to use the existing weak producer sharing path and its ObjectId.

Structured Result entries share the bounded cache LRU and managed Root capacity. Capacity accounting deduplicates physical backing owners, including backing reached through tensor views and affine owners, rather than summing logical tensor sizes. Eviction releases the cache's owner references; callers holding a Result or read window continue to own its backing. `clear()` advances the cache epoch, so an in-flight producer from the previous epoch cannot refill the cleared cache. Cache proof construction, Need replay, and rebinding consume optional cache work. Insufficient optional work or Root capacity skips retention or produces a miss without changing an otherwise successful computation.

Dependency-v2 Result operations have one non-pure case: a Whole, non-joint Atomic output with RequestFailureOnly delivery may clear either purity trait only when it is non-cacheable. Same-run coalescing across distinct but equivalent nodes and weak producer/result sharing across Runs of the same Frozen snapshot both require a pure selected-input producer closure; both use this purity gate independently of the optional cache-work budget. Repeated nonempty Tensor requests for the same impure Whole node and slot reuse its Whole-normalized query within one Run, while distinct impure nodes and consumers whose selected-input closure contains an impure producer remain isolated. Non-pure closures do not participate in either cross-node or cross-Run sharing. Completed-result cache reuse across different snapshots or generations has its own stricter requirements: a pure and cacheable selected-input closure plus successful optional retention.

Retention requires a pure, cacheable operation and a pure, cacheable selected-input producer closure, with no observed backend fallback. `photospider.path_set` is excluded because its fields embed its own ObjectId. A candidate is also excluded when its Result or any source owner is incomplete. The cache currently matches the full tensor footprint exactly: it does not combine entries for mixed `Q` requests, and it may rerun an evicted Whole producer while rebuilding a descendant's current dependency evidence. The C Result ABI does not expose this cache; its implementation is private to the C++ execution runtime.

`ResultBuilder` owns publication. The producer binds descriptor support, writes tensor regions through `publish_tensor`, and supplies a relation and finality for each publication. Tensor regions and their support are checked against the slot's flattened logical sample domain. Overlap, out-of-domain access, incomplete finality, or failed resource admission retires the producer with an error. Sealing checks every field and tensor relation before completing the Result.

For each tensor publication, the builder certifies the supplied relation when its guarantee is not `Unknown`, then restricts every relation to that publication's exact region before accumulating it. Even an `Unknown` relation must match the tensor slot's complete output shape. Separate regions retain separate support, including roles and targets; their union never fills an unpublished gap, and it does not upgrade an `Unknown` guarantee. The restriction stores compact region geometry rather than enumerating the full tensor canvas. The coalescer can recompress a union frontier when later regions close a rectangle; it merges masks only when they share the same underlying witness and output shape and differ along at most one axis, where the intervals overlap or touch. Separated intervals remain separate rather than being replaced by their bounding box. For an `Unknown` relation, `visit_declared()` considers a leaf only inside that leaf's own mask, so a sibling region cannot hide its declared witness. This regional rule applies to tensor samples; field and descriptor relation handling keeps its existing contracts.

`publish_tensor_kernel` lends writable windows for the requested region. For spatial tensors, the builder uses planar rectangles when the complete logical sample byte geometry is representable. If the layout is nonspatial, the sample count cannot be represented, or the full sample count times element width would overflow, the builder allocates affine backing for the requested region under Root limits. This fallback preserves the tensor spec, spatial layout, global sample coordinates, relation, and certified coverage; it changes only the physical writer backing. Callbacks must use each window's `spec()`, `region()`, `sample_axis()`, and the strides returned by `row_run()` or `rectangle_run()`. They must not assume planar backing or contiguous rows. A sparse request over a huge logical spatial domain is charged by its actual writable region, while a larger requested region must still fit Root payload and work limits.

Publication follows the schema policy. `CompleteBundle` hides output until seal. `StablePrefix` and `IndependentChunks` expose only ordered, irrevocable certified field prefixes/ranges; the current publisher does not expose arbitrary out-of-order chunk publication. The callback's `ResultFinality` is an algorithm-author obligation covering data, control, validation, and descriptor facts; the host checks completeness of the declared obligations but does not prove arbitrary callback reads. A later operational failure does not revoke an already certified prefix, and an older descriptor snapshot does not acquire newly published coverage.

The published Result records ordered source ObjectIds for lineage and dependency reporting. That association is metadata, not a strong owner for input payload and not a read grant. `ResultObjectInputs`, `ResultTensorInput` capabilities, and retained windows provide the active owner and authorization paths described above. A physical tensor view also retains every source Result whose bytes it publishes. Result resources retain schema-declared owners, including ICC/OCIO owners named by typed image facets. The compiler selects nested resources from the supplied bindings, and runtime bindings are admitted again under the execution resource root. Public `ResourceMap` and `ResourceVector` containers also carry their allocator and managed ownership; copied results, relations, names, and observations retain root-accounted metadata until those containers and any contained `ResultRef` owners are released. Consumers must budget these copies along with payload and relation work. The policy is conservative, so live owners can retain more backing than the final output alone needs.

## Dependency Evidence & Identity

`ResultRelation` is immutable, bounded evidence mapping each flattened output observation to input support. A support address names the input index, target (`Value`, `Field`, `Tensor`, or `Descriptor`), slot, sample interval, and roles (`Data`, `Control`, `Validation`, `Descriptor`). Roles and targets are part of dirty matching. A descriptor observation is separate from field/tensor sample coordinates; an empty data set can still depend on a runtime count or semantic basis.

### Terminal RequestRecord outputs in C++ and C

A C++ `ObservationKind::RequestRecord` output, or a C ABI 2 output declared as `PS_RESULT_REQUEST_RECORD_V2`, executes once for the selected output's captured semantic-closure query Q. The Result executor does not expand a supplied Q to the full tensor domain just because the operation's region rule is Whole. The continuation must publish one complete, sealed Result with the selected output schema, semantic scope and Root; the selected tensor slot must cover exactly Q. Partial Result publication and mismatched coverage are protocol errors.

The dependency recorder captures one Root-accounted, indivisible manifest for the request. It includes the relations for the published fields and tensor slots, the descriptor witness, and the host's Descriptor/Validation obligations keyed by input port, role, target and slot. Repeated capture or import of the same Result and request identity seeds and merges the prior manifest, so host-added obligations remain present. If an edit intersects any matching support row and role, `potential_dirty` returns the whole Q. An `Unknown` guarantee cannot prove Q clean and produces an unresolved result. The manifest is not an Atomic certificate, and `ExecutionDependencies::restrict` rejects a strict subset of Q.

The selected output and exact Q participate in request identity. Different Q values keep separate manifests. When `ExecutionContextConfig::result_cache_bytes` is positive, completed-result content caching can reuse a matching Q across equivalent fresh Result sources or a renumbered graph when the captured proof matches; cache rebinding creates a new Result identity and retains the terminal marker. Without completed-result retention, identical requests in one execution may still share their active producer. `ResultRef::capture`, weak lookup and cache rebinding preserve the marker. The executor rejects a marked Result as an operation input before starting a consumer; tensor-view publication, checkpoint state and block state also reject it. Pure `ResultProgramPhase::block` work remains available inside a terminal query when its incoming and computed states are ordinary nonterminal Results. C ABI 2 declares `observation_kind` and `failure_delivery` per named output. Its optional CPU `joint` callback supports contracts 1 and 2: contract 1 uses RequestFailureOnly delivery, while contract 2 uses PerAtomOutcome. The singleton callbacks remain required and return ordinary status codes; typed Atom failures and quality attachments are available through contract-2 joint outcomes.

An eligible C++ terminal `RequestRecord`, C `PS_RESULT_REQUEST_RECORD_V2`, or contract-2 joint output uses the host's stateless empty-result path when its tensor Q is Empty and it has no output fields. Static parameter and schema validation, backend selection and operation-resource admission still run. The host checks failure and cancellation, then seals a Result with Empty tensor coverage without invoking producer callbacks or reading inputs. This path does not create an AtomObservation or validation-ledger finality. An ordinary Atomic Empty request still invokes its producer because it may need Control or Validation inputs; an output with fields also runs its producer.

For a structured Result consumer's Tensor Need, the coordinator also uses the ordinary Empty Result path when a computed contract-2 producer's union of requested samples is Empty and its output schema has no fields. Static schema checks, backend selection, and resource admission still apply. This includes a Descriptor-only grant and an Empty payload-role grant. The host supplies a sealed metadata Result without invoking the producer callback, creating an AtomObservation, or finalizing an atom domain. The consumer receives only its `ResultTensorInput`; the grant does not populate `phase.results`, authorize an Object Need, or permit sample reads. Field-bearing computed C2 Empty tensor Needs are not supported by this shortcut. A later nonempty Tensor Need is still expanded into actual atom queries.

`ResultRelation::prefix(budget, count, input, roles, target, slot)` represents an exact inclusive-prefix dependency on the rank-one domain `[0,count)`, where `1 <= count <= UINT64_MAX`. Output `j` depends on input `[0,j+1)`. The relation stores a fixed node and two length-one shape vectors, so metadata size is independent of the domain length. Its role mask may combine Data, Control, and Validation; Descriptor roles or targets are invalid. Visiting an output reports one support span. Projecting requested outputs `Q` emits at most one flattened support span `[0,max_end(Q))`, with no visit for Empty. Inverse projection maps the earliest changed input `k` to `Q ∩ [k,count)`. Projection and inverse work, cancellation, and metadata capacity use bounded resources and return typed failures.

`ResultRelation::neighborhood(budget, shape, radii, periodic, support)` is another compact exact node. It accepts matching tensor coordinates with rank 1..8, positive uint64 extents, and one uint64 radius per axis; the full sample-count product may exceed uint64. It records the radii rather than a per-sample table. For each output sample, its support is the symmetric axis-aligned radius window, clipped to the tensor domain or wrapped on every axis. All-zero radii give identity support. Forward projection expands requested rectangles, while inverse projection returns requested outputs whose neighborhoods intersect the changed input. Wide rectangle projections can represent domains whose sample-count product overflows uint64; enumerating one scalar sample's support may still hit a work limit. Shape/radius/rectangle metadata, work, box count, cancellation, and capacity are bounded by the execution root and query limits. Failure returns a typed status without broadening the support to a bounding box.

The C Result service `make_prefix` creates this relation only between equal rank-one input and output tensor slots. It returns a relation handle for `publish_tensor_with_relation`, and `release_relation` retires the handle. Creating the relation grants no payload-read permission; the callback requests input data separately through `need_tensor`. This C relation helper is independent of the numeric operations: `numeric.ordered_scan` uses the C++ Result phase's prefix relation and checkpoint services, while staged `numeric.mean` and `numeric.variance` use its block-state service.

The C Result service `make_neighborhood` creates the same relation between selected output and input tensor slots when their complete sample shapes match. Its borrowed radii array has one uint64 entry per axis, and periodic must be 0 (clipped) or 1 (wrap every axis). Roles are a nonempty combination of Data, Control, and Validation. The returned relation handle remains owned by the active poll until released with `release_relation`; it can be passed to `publish_tensor_with_relation`. Creating the relation does not authorize reads. Call the service on the poll entry thread, and handle failures as sticky poll errors.

`Exact` means the declared support is complete for the registered operation contract. It does not mean that changed values necessarily change output bits. `Conservative` permits broader support. `Unknown` is unresolved and cannot prove an output clean. Dirty queries compare the captured relation with changed samples and report potential change, not numeric inequality.

Semantic schema identity includes typed slots and semantic metadata, but excludes physical page/tile geometry, storage offsets, object ids, and descriptor revisions. The execution plan includes physical choices when they affect scheduling. Result keys also include the operation contract, parameters, ordered input identities, and captured query. Changing static schema or descriptor facts that require recompilation requires a new plan.

## Limits & Failure Handling

Every `ExecutionContext` creates a managed `ResourceBudget`. If `ExecutionContextConfig::managed_resources` is unset, the context uses default-constructed `ResourceLimits`; an explicit value supplies the configured capacities. `maximum_live_bytes` also caps the Payload dimension. `ExecutionContext::resource_budget()` returns a shared handle for clients that need to account temporary storage, and its leases may outlive the context.

The execution root accounts for payload/backing, work, stages, I/O, relation/map construction, continuations, queue entries, metadata, and retained owners under their configured resource dimensions. Bounds are finite. Oversized relation traversal, payload, or owner admission fails with a resource error rather than returning an incomplete witness. This managed-capacity model covers instrumented resources; it is not an RSS bound.

An output can declare `maximum_output_payload_bytes`. For structured Result operations, the host checks each published Result's physical backing against that per-output cap, deduplicating shared owners and excluding source allocations that remain live through exposed Results or authorized tensor grants. This includes private Whole input backing retained by a `ResultTensorInput`. The check keeps only weak source references, so the cap does not keep input payload alive. Root still charges source and collected input backing; the output cap measures only newly owned output payload. Every prefix publication is checked using the complete Result, which makes the check cumulative as backing is added. A direct singleton, compiled execution, and each contract-2 joint member use the same rule. The first eligible poll allocates the cap guard and shared control block from the Result Root before entering the callback; insufficient Metadata capacity rejects the poll before callback entry. Owner enumeration and comparison consume normal Run and Root work. Exceeding the cap returns `ResourceExhausted` with `CapacityLimit`; contract-2 reports it as a local member failure, and cancellation during member scanning remains local to that member. Workspace, metadata, and ICC/OCIO referenced-resource admission remain separate. The check runs when a Result is published, so a trusted callback's earlier Root allocations are still charged and are not prevented by the cap.

Result publication errors are sticky. Cancellation and stale execution retire active state only after admitted callbacks have returned. A waiter cancellation does not cancel a shared producer while another waiter remains. A failed append or tensor publication cannot be repaired by a later successful callback; a previously certified prefix remains immutable and readable under its captured descriptor. The last owning Result/read-window release retires backing and retained associations.
