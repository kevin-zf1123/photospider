# Managed resources

## Scope and ownership

Each `ExecutionContext` owns a `ResourceBudget`. `ExecutionContextConfig::managed_resources` supplies optional limits, and `resource_budget()` returns a handle to the same root. Reservations and exported storage can outlive the context. Accounting covers declared capacity and instrumented allocations. It does not measure process RSS, thread stacks, unmanaged allocator overhead or ordinary `shared_ptr` control blocks, driver-private memory or provider-owned opaque kernel contexts.

The independent dimensions are Host, Device, Shared, Metadata, Referenced, Entries, Queue and Payload. Host includes Metadata and Shared; Device includes Shared. These overlapping counters must not be added together. The effective Payload limit is the smaller of `maximum_live_bytes` and the configured Payload capacity. A context requires positive `maximum_live_bytes`.

`ResourceLease` copies share one reservation. Admission and growth are atomic and fail with `ResourceExhausted` without waiting for other owners. Capacity stays charged until the last lease retires. Shrinking requires the corresponding storage to have been released or its allocation abandoned. `ResourceBudget::consume` admits cumulative work and stage counts atomically; already issued work is never refunded.

## Plan and preparation

Compilation has structural limits independent of an execution root. `PlanningOptions` defaults to 4,194,304 tasks, 4,194,304 aggregate physical table records, 16,777,216 dependency references and 268,435,456 work units. The static planner checks projected merged records while retaining call lowerings, counts shared incoming tiles once, and admits additional dense-import records before appending them. Local operation graphs have a separate validation envelope because repeated ports can merge into fewer global records. Final validation checks the published program against the requested global limits. Validation exhaustion remains `ResourceExhausted`, including for a custom planner.

Copies of `ExecutionPlan` share the complete immutable program, source IR and static operation/resource owners. Output selection copies the private storage before rebuilding closure and derived tables. `prepare` retains this shared body; compiler-owned tables and immutable resource backing retain their existing ownership and accounting provenance.

`prepare` admits its own Host/Metadata capacity before constructing the `PreparedPlan` state and its layout, kernel, read, output-port and block-work tables. Each prepared kernel wrapper and its module/device owner record retains its own lease. Temporary C++ read/write/output query arrays are admitted before allocation. Operation names, input metadata, scalar parameters and encoded task parameters borrow immutable preparation or Plan owners; preparation does not copy these containers. Input and output schemas share immutable static owners. C module bridge directories use `ResourceAllocator` under the preparation root. The operation's opaque prepared context remains provider-owned; ABI 8 does not declare its allocation size.

PreparedState and kernel wrapper objects, retained operation/device owner wrappers, preparation view arrays and all PreparedPlan table capacities commit their actual host bytes. Native capacity tables commit their array storage; their inline object is already part of PreparedState. Copies of PreparedPlan or PreparedKernel share owners and do not commit twice. Independent preparations own separate tables. Partial preparation failure retires every completed allocation while preserving its peak. Query stack objects and fixed reservation margins are not counted as heap allocation.

Native preparation queries actual allocation capacities and retains a capacity table. Device objects and native kernel wrappers use the context root for their managed metadata. Native driver allocations remain outside the declared-capacity model.

## Context, Run and block admission

The context reserves its CPU queue capacity and worker metadata at construction. Queue capacity stays reserved for the context state's lifetime. GPU submissions use context-wide credits and completion slots owned by each Run; there is no context GPU work FIFO reservation. Separate CPU/GPU admission lists use frame-embedded waiters and allocate no queue nodes. Their context locks and endpoints are included in the context object; frame waiters are stack state.

The context object, CPU FIFO, worker array and Run directory commit their actual host bytes under that reservation. Worker shutdown leaves the arrays allocated until the retained context state is destroyed. Context destruction frees the Run directory and withdraws its bytes even if a PreparedPlan still retains the closed context. A directly constructed internal worker pool counts only its arrays under a supplied parent lease; its stack object is excluded. A partial constructor failure retires completed array allocations after worker shutdown.

`submit` admits Run and maximum-frame bookkeeping before starting execution. Binding preflight uses a budgeted directory of pointers to the supplied bindings, checks names and schemas, captures Result coverage and retains backing owners. It does not copy binding names. External input storage is admitted under Referenced, deduplicated by live owner within the root. Storage already owned by the root keeps its existing charge. Device and Shared bindings also require the prepared device and compiled layout contract.

Run and value-identity owner objects, retained input-identity and delivery-ring arrays, diagnostic state and bounded trace arrays also commit actual metadata bytes. Clearing a retained vector does not withdraw its capacity. Diagnostic state owns a separate lease and can outlive the Run and context through an observation or exported storage owner. Copies share that charge; release on another thread updates the original resource root.

Input tile, identity and canonical-owner directories carry their allocation counters through submission and control-flow edges. A frame takes ownership of the tile and identity arrays; the handoff's canonical directory remains alive through frame construction. Each frame separately counts its canonical directory, hold counters, work slots, lane views and fixed lane completion-message storage. Scheduler task/call arrays, ready queues, submission IDs and skipped IDs count their allocated capacities. Temporary root-marking arrays retire after admission. Stack frame and scheduler objects are excluded. Each array commits after successful allocation and withdraws after destruction, including partial construction failure. These events leave the parent's complete reservation intact until Run cleanup shrinks the transient capacity.

Input binding and frame export reuse a temporary TileView for each physical tile. Its Region, stride and origin arrays commit actual capacities under the Run reservation; input binding allocates only the Region and reuses it for cardinality checks. A Run reserves 256 bytes for the maximum rank-eight view, constructed one at a time before task issue. The stack owner is excluded. Publication copies its retained metadata into Result-owned storage; the temporary arrays are destroyed and their counts withdrawn before the next tile or frame-capacity shrink. Partial construction failure follows the same order.

Each block activation atomically reserves all output capacity plus maximum task scratch per backend and domain multiplied by that backend's active lane count. Native reservations use queried, rounded capacity. Allocation splits this reservation into storage leases; unused capacity is released at block retirement. Exported Results retain their storage leases. A later Run may therefore fail admission while an earlier exported Result remains alive, then succeed after that Result is released.

The Run never expands dependencies or chooses a different placement. `maximum_block_activations` defaults to 1,048,576 and `maximum_work` to 268,435,456. Preparation calculates each block's bookkeeping and COPY work charge. Every activation consumes that charge from the Run limit and context root before entry; even an empty loop has a positive charge. Operation numerical loops are governed by their prepared contract, not by a runtime work-service callback.

Task state, completion slots, bounded failure messages and retirement delivery records are reserved before issue. Invalid or duplicate completion keys abort with `Internal` and `MalformedEnvelope` without allocating or settling another submission. Accepted work retains its invocation, views and storage until completion establishes quiescence. Cancellation stops new work; it does not release accepted work's storage early.

Scheduler failure buffers and the Run's block/terminal diagnostic buffers commit their actual string capacity including the terminator. Settled status copies at most 256 bytes into reserved Run storage without moving scheduler ownership or allocating. Structured error detail is preserved. Each retirement record carries its message-allocation owner through queueing and delivery. The delivery lane releases the record before reporting settlement; a later frame does not overlap an already-settled record's message allocation. Observer copies and the diagnostic returned by `join()` are caller-owned. The latched Run diagnostic remains intact if a caller's `join()` copy fails.

`RunHandle::observation()` retains independent counters without retaining a Run or output Result. It exposes block rejection details, output allocation counts, head waits and current/peak reserved/live output/scratch backing by domain. Export release updates counters even after Run/context destruction. The backing-domain record excludes host metadata; root statistics named `live` still describe admitted capacity. See [parallel execution](Parallel-Execution-Model.md#diagnostics-and-checks) for the fields and timing semantics.

`ResourceStatistics::allocated_metadata_bytes` and `peak_allocated_metadata_bytes` separately count instrumented allocation commits. The current fences cover successfully constructed lease objects, managed allocator blocks, CpuStorage owners, external-reference owner objects, block-allocation bookkeeping and the preparation owners and tables described above. Metadata-mode blocks commit their complete requested allocation, including the alignment header; Payload-mode blocks commit only that header as metadata. A reservation alone commits only its bookkeeping object. Aliases do not charge again, and deallocation on another thread updates the original root. Explicit withdrawal permits capacity shrink after storage release; shrink cannot remove capacity backing still-committed metadata. Quarantine prevents withdrawal; verified settlement re-enables normal withdrawal and retirement. The lease bookkeeping object itself retires normally.

`ExecutionDiagnostics::metadata` reports current and peak reserved/allocated metadata attributed to a Run. Submission bootstrap, coordinator and root-matching nested allocations inherit that Run's observation. Leases retain weak attribution to the original counter owner, so cross-thread release and exported storage update the originating observation without retaining a Run or creating an ownership cycle. Context/PreparedPlan owners and pre-existing input storage retain their prior attribution; concurrent Runs do not duplicate those charges. A foreign resource root does not inherit the active Run's attribution. Existing root `live`/`peak` fields continue to mean reserved capacity; allocated counters exclude allocator-private overhead and RSS.

## Storage and Results

`ResourceAllocator` admits element capacity and its alignment header before allocation. The allocation retains its lease until after physical deallocation. Metadata containers charge Host/Metadata; payload containers additionally charge Payload for their elements. `BufferAllocator::limited()` bounds backing capacity, while `limited_requested()` bounds live requested bytes. Native conversion preserves allocation provenance and charges actual capacity. Root-bound quota/provenance states and reservation owners use managed allocation; parent scope links avoid an unaccounted growable provenance directory. Allocator copies share these owners. Their metadata stays live after payload release until the last allocator or buffer owner retires. An unmanaged caller allocator remains outside execution-root accounting.

Host and native Shared allocation reserve capacity before creating `CpuStorage`. Owner construction and payload allocation commit separately, so a later payload or native bind/map failure preserves the observed metadata peak and then rolls back its live bytes. Capacity sublimit wrappers forward both increments to the original root. Native wrapper objects already allocated through `NativeAllocator` are not committed again by this path.

Block allocation commits its Admission, Slice and EndReservation objects and each successfully allocated directory array. Slice retirement withdraws owner metadata together with released backing while the block can continue protecting reservation. Directory move assignment preserves destruction order. Exported slices retain the Admission owner after block exit; releasing the final export clears its remaining actual counts. External-reference aliases share one registration object and charge its metadata once without counting the borrowed payload as a new allocation.

Result directories, coverage and publication metadata use their selected root. New tensor backing uses Payload; view publication retains existing storage. `capture()` fixes descriptor revision and coverage, so later publication does not widen an older capture. A view retaining source Results keeps their existing backing leases; its own root pays for the new view metadata. Direct publication of external storage uses `reference(storage)` where applicable.

Result envelope and capture objects commit their own bytes after construction, before converting the exclusive owner to a shared owner. Failure to allocate the shared control block therefore retires an already-counted object and preserves its peak. Capturing an existing capture shares that object. Weak references retain no envelope or capture allocation. Per-Result growth-budget objects use `ResourceAllocator` independently, including its managed shared allocation block, so growth owners can retain the budget after the Result envelope is destroyed.

Host and Device tensor spans share immutable metadata objects allocated with `ResourceAllocator`. Their separate metadata reservation covers the ordinary shape, region, stride and origin vectors. Each successful vector copy commits its actual capacity before starting the next copy; partial failure retires completed copies. The metadata object is already counted by its allocator and is not counted a second time. Span copies share these bytes; a new subview owns a separate metadata object and arrays.

`SchemaTemplate::managed_copy` admits and counts each tensor's descriptor shape independently. Keys and batch axes use their managed allocators; batch-axis bytes are not also reserved by the shape lease. Ordinary `ResultTensorSpec` copies create independent ordinary shape storage without retaining the source's shape reservation. Their keys and batch axes follow their allocator copy rules. Move transfers the shape and its lease together. Copy and move assignment destroy replaced members before retiring their former lease. Execution-root admission uses `managed_copy` for the controlled schema.

Read windows count their owned Region arrays. A window's fixed stack object remains outside actual heap bytes even though admission reserves its bookkeeping margin. Composition releases each consumed Region and withdraws its bytes before retaining the source lease; that lease continues to protect its reserved capacity. Nested composition preserves prior source leases without counting released Region arrays again. Moving over an existing window retires the replaced arrays before their leases.

Affine view mapping counts temporary Region dimensions, descriptor shapes, strides, origins and source coordinates under its scratch reservation. Shapes reserve and commit the complete batch-plus-cell rank before filling either part, avoiding intermediate vector growth. Each source piece releases its scratch before the next piece. Affine joining counts its probe coordinate and layout arrays, then constructs the retained TensorSpan from borrowed metadata without an extra origin copy. The read-window joining entry admits its descriptor and join scratch under the window's root. Reshape uses fixed stack arrays for at most eight stride chunks and eight factors per chunk; these arrays require no heap allocation or metadata charge.

Controlled sample descriptors reserve the full batch-plus-cell rank once before constructing their shape, commit actual capacity, and retain the lease until after shape destruction. Sample counting uses checked multiplication without allocating a shape. Footprint `from_regions`, `from_region`, `all` and `none` borrow the caller's shape; `from_region` also borrows its one Region, avoiding an implicit temporary Region/vector copy. Retained shape copies and the temporary whole Region are admitted and committed before later allocation. `close_samples` accounts for descriptor shape, temporary boxes and every box's dimensions, including partial failure.

Footprint normalization counts the canonical box array and each box's dimensions before transferring them to its immutable owner. The owner adds its own object and shape bytes without counting the transferred arrays again. A lease alias protects the arrays through parameter construction and failure unwind. Visit coordinates remain counted through the visitor callback. Tile-cover construction counts its temporary box table and each completed dimension array until normalization returns. Its shape owns a separate lease that moves into the returned Footprint without copying or counting the shape twice. Allocation failure and cancellation release the temporary arrays before their reservations. FragmentAtlasPlan counts retained descriptor and geometry capacities; its allocator already counts the shared owner block and tile table. Automatic geometry reserves the requested rank before filling an empty vector, including one with pre-existing capacity. Copies of either immutable object share their allocations.

FragmentAtlas materialization admits and counts its temporary coordinate array under the active metadata root. The returned descriptor shape and tile geometry have a separate retained lease, with each copy committed before the next allocation. Moves transfer these arrays and their lease together; replacement destroys the old arrays before releasing their reservation. Ordinary Atlas copies create caller-owned geometry and share the packed TensorSpan storage without retaining the source geometry lease. Materialization allocation failure returns `ResourceExhausted` and retires every completed allocation.

Packed and bulk tensor publication count temporary coordinates, chunk Regions, window/layout arrays, descriptor shapes, strides and origins under their admitted scratch reservation. Each successful allocation commits before another allocation can fail, and the guard outlives every covered array. Fixed rank-eight ordering arrays remain on the stack. Canonical window clipping, explicit copying and scalar reads account for their temporary coordinates/Regions and return typed allocation failure. Creating an affine TensorSpan from a window uses the window's resource root.

Input snapshots additionally use their own aggregate-capacity and working-set reservations. Sealing a snapshot reservation releases unused capacity; allocated blocks stay charged until their last owners retire. This quota is distinct from execution-root accounting.

`ImmutableResource` owns immutable bytes and a byte-length/SHA-256 identity. Import copies and hashes; `from_storage` hashes existing storage. `ResourceSet` selects exact declared identities and retains their backing. A Plan and its prepared operation owners retain these resources independently of output Results. `ResourceSet::reference` explicitly admits a set under another root without copying payload.

## Bounds and limitations

Capacity products, alignment and rounding use checked arithmetic before admission. Requests that exactly fill available capacity are accepted. `live` includes reserved but unused capacity; `peak` is the maximum observed admitted capacity. Overflow in allocation or work charges fails rather than wrapping.

The guarantee is `WithinBudgetOrFail` for accounted capacity. Compiler storage, caller-owned bindings, copies made outside managed allocators and provider-private allocations do not acquire an execution-root bound merely by being reachable from a Plan or kernel. Static structural limits, execution work limits and managed memory limits describe separate constraints.
