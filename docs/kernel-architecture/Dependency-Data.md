# Dependency data, execution and ownership

The data API represents exact coverage and immutable dependency evidence. The coordinator schedules Result work and controls callback/error delivery. `ValueFragments` represents typed backing coverage, while `DependencyCertificate` stores execution evidence. Operations use Result protocol 2 and publish structured Results.

## Scope and ownership

Structured Result execution combines exact logical coverage, typed input capabilities, host-owned continuations and Root resource admission. `Footprint` owns coverage metadata, `ValueFragments` retains typed backing owners, and `DependencyCertificate` stores relation rows without retaining pixels. Result continuations use `ResultObjectNeed`, `ResultTensorNeed`, `ResultIoRequest` and `ResultRelation`.

```text
requested Result roots
        |
        v
Root-owned Actor registry -> ready frontier -> context worker queues
        ^                                     |
        |           Need or publication       v
        +------ coordinator satisfies Needs < callback
                       |
                 Root admission
```

The coordinator advances dependency-ready Result Actors without occupying a worker while it waits for an upstream producer. Ready callbacks compete for the configured worker capacity and Root resource limits.

Each callback borrows its phase and service references until return. The Run retains continuation state and admitted output/scratch leases; `ValueFragments` retains its supplied Value storage owners independently.

class Footprint final {
 public:
  static Result<Footprint> from_regions(
      std::vector<std::uint64_t> shape, const std::vector<Region>& boxes,
      const FootprintLimits& limits = {},
      std::uint64_t* consumed_work = nullptr);
};

class ValueFragments final {

  static Result<ValueFragments> create(
      ValueDescriptor descriptor, std::vector<ValueFacet> facets,

      const FootprintLimits& limits = {}, ResourceBindings resources = {});
  Status read(const std::vector<std::uint64_t>& coordinate, void* destination,

## Core data structures and memory

`Footprint` is an exact set in a nonzero rank-1..8 logical domain. Its canonical disjoint rectangles represent Empty, All and non-contiguous coverage. Recursive axis sweeps merge adjacent intervals only when their suffix sets are identical, so construction order, duplicate boxes and alternative tilings do not affect set equality. All remains compressed even when the dense element product would overflow. Union, intersection and difference require the same domain and retain holes. `tile_cover(geometry)` returns exactly the touched tile coordinates in a ceil-divided domain; it does not mark every sample inside those tiles valid. `visit` emits each sample once in row-major order under an explicit sample limit.

`FootprintLimits` bounds each operation's candidates and box counts, including duplicate construction work. Exceeding limits returns ResourceExhausted; cancellation returns Cancelled. Neither outcome is Empty or a bounding-box approximation. Compound users must additionally bound their total operation and metadata work across calls; a per-set limit is not a whole execution budget.

`ValueFragments` pairs complete descriptor/facets with an authorized Footprint and retained rectangular Values. Construction clips supplied coverage, rejects missing authorized samples and rejects inconsistent overlapping owners/mappings. Equivalent origin-relative mappings on the same owner deduplicate. Validated ColorArray tuples require complete channel coverage. Structural image values are rejected from this Value container; tensor data is carried by a typed Result tensor slot and read through `ResultTensorInput`. `read` uses Value's checked signed-stride addressing and copies the actual dtype width. A hole, unauthorized address or wrong width is an error; there is no synchronous fetch, implicit extension or zero-fill fallback. `restrict` restricts owners and coverage together. `collect` requires a complete rectangle before allocating through the supplied BufferAllocator. Retained capacity counts unique actual storage owners, independently of valid coverage.

`DependencyCertificate` stores an identity, exact observation coverage, declared input domains and one `AtomCertificate` per covered observation. `ResultRelation` records typed Value, field, tensor or descriptor support, including the selected slot and roles. An explicitly present empty row is known empty; an omitted row is unknown and cannot be published as resolved coverage. Identity binds the caller's access, numeric and error contract and snapshot; these data types cannot prove that an arbitrary callback followed its declared reads.

`restrict(P)` rejects any P outside coverage. `backward(P)` unions just those rows for transport, grouped by port/role. This fetch projection is not a certificate. `transpose(dirty)` returns exactly covered observations whose same-port, matching-role sample or tagged support intersects the edit. `merge` requires equal identities/domains and equal canonical rows on overlapping observations. A request-level failure witness or terminal RequestRecord is not an atomic success certificate.

The internal `DirtyDeltaQueue` keeps accumulated and propagated Footprints for each record in one certificate generation. Under one mutex, taking an item computes accumulated minus propagated, records propagation and clears queued. A later new atom can enqueue the record again. Dependency structure belongs to the demand coordinator independently of pixel cache ownership; the queue itself owns no pixels or workers. A failed downstream enqueue must fail its generation.

Focused checks are `test_footprint`, `test_value_fragments`, `test_dependency`, `test_dependency_dirty` and `test_input_snapshot`. They exercise independent finite membership/reachability oracles, unknown rows, identity/swap, role/tag isolation, late dirty waves, dtype/stride/owner bounds and snapshot COW. See [Cache Model](Cache-Model.md) for generic snapshot identity and ownership.

## Execution and state machine

`OperationTraits` uses semantic version 25 and Result protocol 2. Result traits describe `Atomic` or terminal `RequestRecord` behavior, failure delivery, continuation/workspace bounds, and typed output ports. Staged Result programs require deterministic, side-effect-free behavior except for the declared Whole Atomic RequestFailureOnly case. Compilation checks executable edges reachable from requested outputs and side-effect roots. It computes EffectiveAtomic over each output's relevant input ancestry; RequestRecord cannot feed an active consumer. Excluded ports retain static metadata without running a producer. Result plans retain unresolved input demands rather than inventing a rectangular approximation. Ordinary execution runs every non-side-effect-free operation as a mandatory root, including operations without requested named outputs. Fragment and atom execution do so only when the query contains a nonempty demand; a completely empty query skips unrelated effect roots. Within a Run, an effectful tensor output uses slot zero and full coverage for its internal actor identity, so later requests reuse that actor. This does not widen authorization for other slots: each slot still requires its own Need and valid publication coverage. Effectful work is not shared or cached across Runs. A mandatory root failure or cancellation fails the enclosing Run.

Operation execution uses `start_result`; its query captures one selected output and tensor-slot demand. A staged poll can request Control samples before the corresponding Data samples. It requests Result objects, tensor samples or closed I/O through `ResultObjectNeed`, `ResultTensorNeed` and `ResultIoRequest`. Successful publication carries a `ResultRelation` for the consumed Control and Data support. `Exact`, `Conservative` and `Unknown` keep their meanings through composition and dirty queries. C++ RequestRecord and Result continuations preserve the selected output's captured query; a RequestRecord query Q remains one terminal observation and is not widened by a Whole region rule. The Result C table is ABI 2 and the only operation-plugin C interface. C operations require registry preparation before inference or start. When `resolve_metadata` is present, preparation validates the complete inputs and then calls the resolver; for a fixed-schema operation, the importer installs `specialize_metadata` to validate input prototypes and return the declared outputs. Direct callers must use the registry preparation/resolution path first. Output records declare `observation_kind` and `failure_delivery`: operations without contract-2 joint callbacks use RequestFailureOnly; contract-2 operations use PerAtomOutcome. Singleton callbacks remain required and return ordinary C status codes; typed Atom failures and quality attachments are available through contract-2 joint outcomes.

Each `ps_result_output_v2` also carries an immutable view policy and optional output payload bound. `PRESERVE_VIEWS` is valid for a CPU, non-joint Atomic output; `REQUIRE_INPUT_VIEWS` implies it and requires CPU Whole execution. In compiled structured CPU Whole execution, the coordinator validates a payload Tensor Need, prepares its authorized boxes before the computation poll, and either proves affine views or applies Auto collection. A direct registry start does not synthesize this Need preparation. `PAYLOAD_BOUND` enables `maximum_output_payload_bytes`, where zero is an explicit limit; with the flag clear the byte field must be zero. The bound is supported for CPU Whole or staged output and is checked at publication, with the existing member-local handling in joint execution. Root accounting for input backing, workspace, metadata and work remains separate. The importer rejects unknown or inconsistent flags, and the resolved `query.output` exposes the registered policy to both `start` and `poll`; metadata resolution can refine the output port/schema but cannot change the policy. These tail fields change the nested output-record layout while the C ABI remains version 2. Exact `struct_size` validation rejects old prefix records, so C modules must rebuild; there is no compatibility shim.

Result discovery, poll counts, continuation state, output/scratch and GPU tables have finite limits. Reads, explicit work charges and allocation failures are sticky even if a callback ignores their returned Status. Failure observers cannot prevent another observer from receiving the error. The first recorded failure remains the reported cause, while the host separately vetoes CPU fallback after any nonretryable typed failure; only an unqualified `BackendUnavailable` with permitted origin and scope can remain retryable. Accepted-call failures retire continuation state once and release input owners before cancellation is applied. Poll admission is nonblocking: overlapping or reentrant calls return `InvalidArgument/Protocol/Group` without entering the callback, notifying failure observers, recording a failure latch, or modifying the active phase, first failure, or work count. Borrowed phase/query/service references expire on callback return, concurrent move or destruction is forbidden, and continuations must use their granted allocators. `start_result` checks cancellation around its factory; cancellation observed after factory entry takes precedence over factory, allocation, and returned-state validation errors, and any returned state is destroyed before return while the definition lease remains alive.

Structured Result execution uses a Root-owned Actor registry and pending-task list. The coordinator submits ready callbacks through the existing CPU worker queue or selected native GPU queue. A worker does not wait for an upstream Result producer. Each stage uses nonblocking admission against the shared Root budget; sealing releases unused capacity while retained state, input and output leases remain charged. A request that cannot fit its minimum working set fails with `ResourceExhausted`. Result callbacks use `ResultTensorInput` for authorized reads. An allocation may escape a Result callback only after the host imports it through the controlled allocator.

For a staged Result RequestRecord, the captured semantic-closure Q is executed once and published as one complete sealed Result for that exact Q. Frozen execution retains its captured graph and input owners. Root Actors are submitted in bounded callback waves and the coordinator applies each wave after its submitted callbacks retire. See [Cache Model](Cache-Model.md) for active demand reuse and completed-result retention. C++ staged GPU fragment access uses the [Fragment Atlas](Fragment-Atlas.md), and bounded native discovery is described in [GPU Discovery](GPU-Discovery.md).

The [dependency sampling document](Dependency-Sampling.md) describes the STMap helper contract and generic radius operations. `image.stmap`, `numeric.radius_gather`, and `numeric.radius_scatter` use structured Result dependency execution; the STMap operation publishes a typed image Result, while the radius operations publish generic numeric Results. See [Image operations](Image-Operations.md) for their input contracts. Optional pure static validators run during compilation and before direct Empty-query state decisions.

## Structured Result tensor dependencies

Structured Result callbacks use `ResultTensorNeed` and `ResultObjectNeed` records, with `ResultIoRequest` for mandatory I/O. `ResultTensorNeed` names an input, tensor slot, Footprint in that tensor's complete logical sample shape, and a role; the sample shape includes batch axes before cell axes. The coordinator checks the Need against the input Result schema and certified coverage before exposing `ResultTensorInput`. That capability authorizes exactly the requested samples and starts no hidden reads.

When any structured Result consumer requests samples from a computed C2 producer, structured execution expands the request into singleton-atom source queries, up to `min(65,536, maximum_boxes)`, and schedules those requests in cohorts of up to 64. If the consumer is a C2 member, it still represents one output observation, while its input Tensor Need can span multiple source observations; the expansion supplies that region as private `ResultTensorInput` pieces. Each piece retains the original ResultRef, its captured descriptor and its granted samples. The coordinator does not synthesize an aggregate Result or validation domain. The Need cache fingerprint includes the captured facts of every piece. This behavior does not narrow wider computed Tensor Needs on other paths. Read and window acquisition recheck each piece's grants. A compound capability's `object_id()` is zero because it has no single Result identity; that zero ID itself grants neither payload access nor Object-Need authority. Reads and windows remain authorized by each piece's Tensor Need, while `result_descriptor` requires an explicit Object Need. The phase association continues to list every real input port and ObjectId.

The composed read window retains the original owners and leases, including those keeping field pages, associations or resource-backed storage alive. It combines already authorized backing without copying tensor payload. View publication continues to use the existing affine-transform or ordered planar-plane paths, each with its own physical mapping requirements and source-owner retention. Composition does not relax those requirements; several pieces alone do not guarantee that either path can publish one view. The multi-piece expansion handles tensor Needs and does not implement wide Object or Field aggregation. A collection-only C2 Field result remains usable through its ordinary Object Need and field I/O path; `field_collector` in `test_result_atoms.cpp` covers this one-row flow, not general aggregation.

When a computed C2 producer has no fields and the union of a Tensor Need is Empty, the coordinator uses the metadata-only Empty Result path instead of expanding atom queries. Descriptor-only and empty-payload-role grants are included; the sealed Empty metadata Result authorizes no sample reads and does not finalize an atom domain. A later nonempty Need is expanded into real atom queries. An Empty C2 Tensor Need from a producer with fields is still outside the supported expansion.

`compound_profile_owners` in `test_result_atoms.cpp` checks how a 65-piece tensor window retains each source Result and its associated field/profile backing through a valid affine view and a loaded output window. The pieces in that fixture share compatible tensor backing; composition does not authorize arbitrary fragmented mappings.

In the C bridge, `result_descriptor(input, ...)` requires an explicit Result Object Need for that input. A tensor or field Need does not grant descriptor access; an absent Object Need returns sticky `InvalidArgument` with `UnauthorizedRead` and Protocol/Group detail. `acquire_tensor_window` can still return a valid compound window whose `object_id` is zero. The `result_atoms_fixture.c` and `test_result_c_atoms` coverage exercises 65-source reads, a sticky sparse-hole read failure, the missing-Object-Need descriptor failure, retained tensor/window access across polls, and common-storage view publication. The retained inputs remain readable after context retirement, and releasing the final owner returns their Root accounting. The C++ `test_result_atoms` additionally checks pre-cancelled demand and Host admission exhaustion followed by recovery. Neither test establishes behavior for cancellation during window acquisition or a partial-window fault.

A callback may stage its work. For example, it requests Control tensor samples, reads them in a later poll, and then requests only the selected Data tensor samples. The final publication carries a `ResultRelation` row for every output observation, including consumed Control support and selected Data support. An unconsumed control coordinate produces no relation edge, and a tile boundary does not make every sample in that tile a dependency.

`ResultRelation` is immutable structural evidence. Its tensor support uses logical sample coordinates in the complete sample shape, including batch axes before cell axes. Each support address retains the target and tensor slot, and its roles distinguish Data, Control, Validation, and Descriptor. Tensor description facets and other declared semantic descriptor facts are consumed through the corresponding Descriptor/Validation support; layout group metadata does not invent sample support. Relation ancestry records the original Need port so replacement can rebind evidence through the same logical input. A Result runtime descriptor witness can be transposed with role `Descriptor` (bit 8); static input tensor schema descriptor/facet changes are static and require recompilation, so static input tensor dirty queries accept payload roles 1..7. `visit_declared()` enumerates declared known spans, including spans reachable in an Unknown relation, for representation/projection validation. Its success does not prove relation completeness or cleanliness; ordinary `visit()` and `intersects()` keep Unknown unresolved. `Exact` permits a clean answer only for complete captured coverage, `Conservative` may widen potential dirty, and `Unknown` remains unresolved.

During compiled structured Tensor publication, the host also checks ColorArray tuple closure for each published tensor region and corresponding input port/slot. A Data mapping must have same-observation Validation support for the complete channel tuple; evidence from another observation, port or slot cannot fill a gap. Output observations are grouped over both schema-declared `atomic_trailing_axes` and the implicit typed ColorArray channel axis. The compact proof handles grouped Data/Validation role-5 mappings, including identity views. When those mappings need a more exact check, the validator projects the requested output Footprint and visits declared support under Run-work and cancellation limits; it does not enumerate the dense input domain. Exhausting those limits returns an error instead of widening support. `SchemaTemplate::validate` rejects a ColorArray tensor with `atomic_trailing_axes > 1`. These checks apply to compiled structured Tensor publications; they do not claim closure validation for field or direct continuation publications. A ResultRef may still acquire an authorized partial tensor window, while `ResultBuilder` requires each ColorArray publication region to contain complete tuples.

For each tensor publication, the builder certifies the relation for submitted samples only when its guarantee is not `Unknown`; every relation, including `Unknown`, must match the tensor slot's complete output shape and is restricted to the exact publication region. Disjoint regions keep their own source spans, roles, and targets; union does not widen support across a hole or upgrade `Unknown`. Restricted relations store bounded region masks instead of enumerating the full tensor canvas. The coalescer revisits the flattened union frontier as regions arrive, merging masks only when they share the same child witness and output shape and differ along at most one axis whose intervals overlap or touch. Separated intervals remain separate rather than becoming a bounding box. For `Unknown` leaves, `visit_declared()` respects each leaf's own region mask, so a sibling mask cannot hide a declared witness inside that leaf's region. `test_global_results.cpp` covers mixed Exact/Unknown disjoint supports, nested unions, a same-element-count wrong-shape rejection, and frontier compaction that keeps unfilled points unresolved. `test_result_plugin.cpp::many_view_windows` exercises both 1,024-by-1 and 1,024-by-2 frame/layer views (up to 2,048 windows) within the existing Run-work limit. Descriptor and field relation rules are unchanged.

`ExecutionDependencies` and shared dependency manifests retain relation evidence and source associations without retaining pixel payloads, `ResultRef` owners, source callbacks, or workers. The published `ResultRef` separately owns its typed tensor backing and may retain consumed input Result owners through its monotone association. A `ResultRef::capture()` couples descriptor, relations and dependency evidence to one certified revision; the host actor publishes that captured view. When `DemandHandle::replace_bindings` commits new immutable inputs, it compares bytes over the old evidence's source support and calculates potential dirty through the captured relation. A changed consumed Control sample dirties the old output relation; the next request discovers new Data support under the new binding generation. Unconsumed controls remain clean. Semantic-alias diamond ancestry rebind is covered by the focused Result contract fixture. Earlier evidence remains immutable and continues to describe the earlier generation.

Each Result dependency record belongs to one logical output target, typed member and query scope. The scope is a domain-separated SHA-256 of the full public semantic key; it separates Q identities without changing that public key. A record stores consumed upstream query identity, support kind and slot for each input port. Capture and restriction retain only edges that reach the same typed child record, while dirty propagation and cache rebind follow those exact port/scope/kind/slot edges rather than merging requests for the same producer. WorkflowInput changes fan out to each subscribed query scope, while computed-input changes travel only along their recorded edges. If a consumer sees the same producer object again on the same port, its payload-free dependency bundle retains the greatest observed revision. A terminal RequestRecord retains its complete Q and manifest as one indivisible record.

An immutable `DependencyBundle` can be reused when its plan position, snapshot, routes, coverage, scope, relations and typed child edges still match. Cached record rebinding returns an existing structural owner when its record identity binds the current plan and snapshot and its logical step, routes and child mappings are unchanged. A different logical step or plan follows the current routes; aliases can be remapped when their child routes are unambiguous. Rebinding shares immutable relation owners and copies structural metadata, not payload. A captured `ResultRef` keeps its own bundle, so later changes to the Run's mutable record builder do not rewrite earlier evidence. The builder moves its records into the final result only when no Actor has pending work and every Actor is complete or terminal. While a producer may still be serving a peer, the Run returns a snapshot copy and retains its mutable builder. Record entries and capture/rebind traversal consume Root capacity and bounded Run work; Result objects separately own payload.

Within one Run, the structured actor registry keys an active request by its compiled output template, snapshot, selected output or tensor slot, request kind, and canonical query Q. Equal keys reuse the same Actor; a different Q gets an independent Actor. The separate dependency scope is a domain-separated digest of this full semantic key; the public semantic key itself is unchanged. The registry strongly retains pending actors and keeps only a weak observation after completion, except that contract-2 Actors remain registered through first delivery. The public `ExecutionContext::execute_atoms` entry point preflights named CPU Result queries, expands their requested sample footprints into observation keys, and collects each Result with its Q-scoped dependency root. It does not merge distinct Q values into one observation. A per-step alias points to the latest request for that logical step, while another owner is required to keep a completed Actor available for weak lookup under the contract-1 policy.

`ExecutionOptions::result_publication` notifications are scoped to one caller. The subscription tracks revision watermarks by logical step and `ResultRef` object identity, so a non-increasing revision of the same object is suppressed but a different object at the same step starts a separate stream. Each notification reclaims at most eight expired weak watermark entries. Aliases are notified independently; each receives the captured certified view for the same published object.

The logical sample relation is the evidence consumed by dependency and dirty queries. Tile projections may batch physical I/O, but they cannot replace that relation or certify unrelated samples as read. A C++ terminal `RequestRecord`, C `PS_RESULT_REQUEST_RECORD_V2`, or contract-2 joint output with Empty tensor coverage and no fields uses the host stateless path: static checks and resource admission run, then the host seals the empty Result without producer callbacks or input reads. This path does not create an AtomObservation or validation-ledger finality. An ordinary Atomic Empty demand may still require Control or Validation reads; outputs with fields also run their producer. Public `ResourceMap` and `ResourceVector` results own root-accounted metadata. A copied coverage map, source observation vector, or Result output map retains its names, map/vector storage, and any contained Result owners until released. Consumers should move or release these containers when their data is no longer needed and include retained copies in the same resource plan as payload and relation work. Resource limits bound continuation state, I/O, relation/maps, payload, queueing, work, and retained owners under the same execution root.

## C staged-program contract

The Result ABI 2 C operation table is the only C staged-operation interface. It exposes typed Result ports, callback-scoped services, staged Needs and Result publication. The loader validates and copies its bounded table before atomically publishing definitions, and retains the module owner while imported callbacks can run. The C++ API uses the same staged Result model through `ResultContinuation`; Result ABI 2 remains the sole C operation-plugin interface.

A poll submits per-output associations with exact runs, ports, roles and tagged evidence. Atomic coordinates name the current sample or HW pixel; terminal associations use no atomic coordinate and retain the complete original Q. Returning Need after allocating output, or completing with unresolved needs or unpublished output, is an error. Descriptor runs cannot encode holes as data.

The phase services expose checked sample reads and borrowed fragment views with actual dtype, origin, signed strides, byte span and authorized region. Missing samples never trigger hidden upstream reads. Cross-poll input ownership requires `retain_input`; its handle preserves exactly that fragment's authorization and underlying storage lease. Invalid handles and ignored service failures are sticky.

| Resource | Validity and ownership |
| --- | --- |
| Borrowed fragment view | Valid through the current poll callback; the underlying supplied owner remains retained by the Run. |
| Retained input handle | Monotonic and unique within the invocation; valid until release or state destruction; preserves only the retained fragment's authorized region and storage lease. |
| Scratch pointer | Valid through the current poll callback; expires when poll returns. |
| Output pointer | Valid until successful publication, or until poll returns if unpublished; publication revokes direct pointer access immediately. |

### C checkpoint services

The C Result services `checkpoint_before`, `checkpoint_read`, and `checkpoint_publish` expose the Result checkpoint path for pure staged operations. A lookup returns the greatest stored sequence no greater than the requested bound. A miss succeeds with handle zero; a hit returns an opaque handle, sequence, and canonical tensor byte size. The opaque handle is usable only during the current start or poll callback; its callback-epoch entry retains the state and witness, and joint-poll handles are isolated by member.

Checkpoint state is a sealed generic `CompleteBundle` Result with one fully covered tensor and no fields, metadata, or domain; its tensor has no facets, groups, batch axes, or spatial layout. `create_block_state` copies a byte payload into that Result and checks the payload size against the tensor's logical samples. The caller can use the resulting operation-owned handle as block state or pass it to `checkpoint_publish`. Block-state handles remain valid across polls until released or the callback state is destroyed. When optional retention is admitted, publishing retains the Result and successful dependency witness. The call does not consume the handle; the caller must still release it with `release_block_state`.

`checkpoint_read` copies a positive in-bounds byte interval in canonical row-major logical sample order. The interval may start or end inside an element and may cross sample boundaries. The service exposes no pointer to retained storage, charges read work, and checks Root capacity and cancellation. A restored checkpoint reimports its successful dependency history, facts, ancestry and association; it does not restore Result input capabilities or authorize new input reads. The callback must request current inputs separately. Checkpoint APIs require a nonzero phase and a deterministic, side-effect-free operation. RequestRecord operations, block callbacks, and GPU discovery cannot use them. Invalid handles, intervals, scope or prohibited use become sticky failures.

For optional `checkpoint_publish` retention, the coordinator walks the actual input bundles consumed by the callback and measures their unique structural DAG. It counts each `DependencyRecord` and immutable relation owner once. The metadata weight includes scopes, typed port queries, sample footprints, domains, routes, manifests, certificates and association records; admission checks cache metadata capacity and `dependencies.sets.maximum_boxes`, while traversal consumes `maximum_dependency_cache_work`. If an optional limit is exceeded, the host skips retaining the checkpoint and computation continues.

Finiteness is enforced by this fixture's scan logic; the generic Float64 checkpoint service copies canonical bytes and does not reject non-finite values by itself.

## Runtime structural evidence

`ExecutionResult::dependencies` owns immutable direct records for a successful structured dependency-network Run. Records preserve merged Atomic certificate rows and their exact coverage; each Whole or terminal RequestRecord keeps an indivisible manifest. Atom collection adds one named root per observation Q scope; related Field and Tensor records remain attached through their typed logical mappings. Multiple atom observations under one requested name therefore retain separate query roots in the same evidence object. The builder merges only matching node/contract/snapshot rows. Source declarations, records, subscriptions and named roots share a bounded metadata count, separate from controlled pixel bytes. Evidence owns no Values, source callbacks, snapshot blocks or workers and remains usable after pixel results, the graph, registry and ExecutionContext have retired.

`coverage()` states the named output samples for which the evidence is complete. `certificate(node)` returns observed Atomic rows; an absent node, Whole record or terminal request returns NotFound. None of those outcomes means unknown rows are clean. `potential_dirty(input, samples)` is exact for the captured relation and those named output subsets. It routes only direct subscriptions using the real `DirtyDeltaQueue`; a record receiving a later disjoint delta propagates again in the same query generation. Source Footprint copying, traversal and answer growth are bounded, with cancellation and explicit ResourceExhausted failures. A failed query never returns a partial clean/dirty map.

This query handles payload changes under fixed declarations. Static static input tensor schema descriptor/facet changes require recompilation and are not accepted as dirty sample edits. Typed Result runtime descriptor observations are represented by role bit 8 and can be transposed through the captured relation; Result descriptor/schema changes that alter the compiled schema still require recompilation. The sample record graph does not model cross-node metadata-output atoms. Direct nonspatial tags remain present in each certificate and may be transposed through that node's certificate; the API does not infer a clean upstream metadata result when no metadata-output atom was recorded.

`restrict({name: subset})` walks the stored direct associations backward and restricts all contributing Atomic rows and subscriptions together, discarding unused records and roots. Unknown coverage is rejected. Nonempty Whole subsets retain their complete global manifest; Terminal RequestRecord permits only its identical full Q. Empty Atomic coverage is known empty, while an omitted output name is absent. An output record whose original query is Empty can still carry recorded non-payload Control or Validation obligations; restricting it to Empty preserves those obligations and their upstream records, including across repeated restrictions. Restricting a previously nonempty output to Empty removes its payload obligations and support. For a named Result atom root, the Empty restriction preserves the named output namespace. This operation reads no pixels and does not invoke callbacks.

## Exact demands and immutable binding replacement

`ExecutionContext::open_demand(plan, bindings)` pins the current graph contract and immutable Result bindings. A `DemandHandle` shares that bundle and generation across copies. `request({name: Footprint})` returns named ResultRefs, diagnostics and structural evidence. Every request keeps its original Q. Result continuations receive selected tensor slots through typed Needs. A staged terminal RequestRecord retains the complete captured query for its selected output. For a Result RequestRecord, supplied tensor Q remains the exact terminal observation even when the region rule is Whole. An Empty tensor request with no output fields on a terminal RequestRecord or contract-2 joint output validates static metadata, backend and resources, then takes the host stateless path without producer callbacks or input reads; it does not manufacture an AtomObservation or validation-ledger finality. Ordinary Atomic Empty requests may still require Control or Validation inputs, and outputs with fields run their producer. Unrequested names are absent. `execute_fragments(frozen, Q)` provides the same exact query for an explicitly pinned bundle, with result generation zero.

Successful requests capture immutable structural publications for their exact named queries. `replace_bindings` compares immutable bytes against captured source support, computes potential dirty through the old associations, and commits the new bundle, generation, and accumulated dirty together. No caller dirty hint is trusted. Changed consumed Control evidence remains dirty until that exact query is successfully republished, even if the output value happens to remain equal. A new request may discover a different Data sample or Result tensor slot under the replacement control values; the new relation replaces support for the new generation while prior evidence remains unchanged. `source_support()` is the bounded fetch union for byte comparisons and does not replace per-output relations. ColorArray tuple comparisons include full C; generic comparisons preserve all dtype bit patterns. Static input tensor schema descriptor/facet changes and Result schema changes that alter the compiled contract require a new plan; typed Result runtime descriptor edits use declared Descriptor or Validation support and can participate in dirty queries. Tensor semantic metadata and descriptor edits are represented by declared support, not inferred from tile geometry.

Replacement validates all bindings before publication. Sample, metadata or validation failures retain the old generation. A racing request publication or replacement returns Stale for retry. Latest requests captured before a completed replacement cannot publish into the new generation; cancellation takes priority over Stale. `freeze()` pins the current immutable bundle independently of future edits. `release(Q)` drops one exact subscription without cancelling active requests, which may subsequently republish it; `cancel()` stops that handle and retires its publications and bundle. Context destruction cancels and drains active demand calls before retiring its existing workers. Direct context calls must not race context destruction, while existing handle calls may do so. Input owner destructors run outside the publication mutex.

`maximum_demands` bounds live uncancelled handles (1..65536, default 1024), and active demand calls are bounded by the existing queue plus CPU worker capacity and one coordinator slot. `DemandConfig::maximum_metadata_entries` bounds each handle's retained query/evidence/dirty metadata (1..1048576, default 65536). A handle owns no workers or pixel cache. Structured Result producers use the existing CPU/GPU pools, WaitingAdmission and accounted allocator; compatible producers share through `SharedResults`. Completed-result content reuse uses the optional pixel LRU with bounded structural proofs, as described in [Cache Model](Cache-Model.md). See [Fragment Atlas](Fragment-Atlas.md) for exact GPU input transport and CPU fallback.

## Active Result demand sharing

The demand coordinator and Root-owned `SharedResults` directory share compatible structured Result producer work for the same immutable bundle and exact selected query. A query key includes the captured bundle, plan/operation contract, node, geometry, selected output and resource policy. Sharing and caching require a deterministic, side-effect-free selected input closure; projected-out inputs do not affect eligibility. A side-effectful or non-deterministic ancestor blocks downstream sharing even when the consumer is pure. The coordinator keeps waiter cancellation and currentness separate from the producer lease, so one cancelled waiter does not cancel work still needed by another request. Callback workers do not wait for upstream producers.

Shared Result entries and waiters use their own Root `Entries`, `Host` and `Metadata` admission. `ExecutionContextConfig::maximum_result_checkpoint_scopes` bounds only the Result checkpoint-scope directory (1..1,048,576, default 65,536); it does not limit active Result sharing. When a consumer adopts a completed shared Result, the coordinator imports its captured dependency bundle and records the captured descriptor revision on the Actor. Validation ancestry from the frozen publication therefore remains available to dirty propagation. Context shutdown drains demand calls and submitted callbacks before retiring workers. `cache_statistics()` combines retained-result-cache observations with structured Result sharing counters while preserving each source's counter scope. Active producer epochs remain visible even when completed-result retention is disabled.

Their fixtures exercise producer-wave admission, an independently running smaller Q, joint outcome isolation and `numeric.ordered_scan`. Block cache observations in these tests are implementation details.

## Result block state transitions

`ResultProgramPhase::block` and the C block service operate on an explicit sealed `CompleteBundle` tensor state. A block callback reads that state and returns it or a newly created state; it does not issue Needs or publish the operation output. The producer requests any later tensor samples from its poll callback. Checkpoint and block services remain separate: checkpoint restoration can import successful dependency evidence, while block state carries only transition data. Optional block-state retention may skip a transition or recompute it under resource limits. Its hit counts and transition reuse are implementation details, not performance promises.

## Result joint contracts

Joint callbacks use the structured Result protocol through `OperationDefinition::start_result_joint` and `OperationRegistry::start_result_joint`. Joint callbacks are an optional grouped Result execution contract. The Result joint contracts and their direct and structured execution paths are described below.

### Structured Result joint callbacks

`OperationDefinition::start_result_joint` provides direct CPU joint callbacks for structured Result outputs; `OperationRegistry::start_result_joint` starts a continuation. Both contracts require Atomic outputs from one prepared static invocation, matching input metadata and parameters, CPU backend. Contract 1 requires RequestFailureOnly delivery and accepts 2..64 distinct output indices. Contract 2 requires PerAtomOutcome delivery and accepts 1..64 distinct `AtomKey` members; different coordinates may name the same output, but all members of one output use the same tensor slot. The snapshot identity groups routing provenance and does not provide numeric input semantics.

For each tensor member, start captures the raw tensor Q, closes it over tuple channels and atomic trailing axes, and requires one nonempty Atomic observation. Every other sample axis must select one coordinate. `result_atom_key(query)` encodes the output index and remaining coordinates, including batch axes; tuple and atomic trailing axes are omitted. `result_observation_domain(query)` returns the complete fixed domain over those remaining axes. A collection-only output maps to the singleton key at coordinate zero. The shared start callback receives closed queries for non-cancelled members, which may be a one-member subset. Each poll checks the raw Q, then revalidates prepared schemas, static parameters, and backend before lending the closed query. The registry retains the definition, prepared invocation, keys, cancellation tokens, continuation, and Root-owned resources.

Each poll invokes the callback once for the ready non-cancelled subset. It returns one Root-owned `ResultJointOutcome` for each member, keyed by `AtomKey`: a Result tensor/field Need, complete Result publication, or local failure. Contract-1 keys use distinct outputs; contract 2 can return different coordinates of one output. The host checks the whole envelope before exposing outcomes, including Root ownership of the outcome vector and nested Need containers, member count and identities, selected input projection, Need slots/shapes/roles, field indices, and publication against each member's closed query. Cumulative Result Need entries across the round are capped at 65,536. The host precharges each Need envelope's entry count before validating its entries. A malformed envelope fails the continuation with a sticky group error; valid member-local errors remain attached to their outputs. Cancellation is returned per member and cancelled members are omitted from the callback.

Before exposing a round, the host validates ColorArray tensor transport separately for each member, input port and tensor slot. It unions that member's Data, Control and Validation requests for the same port and slot, then requires the union to contain the complete channel tuple. Separate requests from one member can supply the tuple together; requests from another member, port or slot cannot fill a gap, and the host does not synthesize missing channels. Descriptor-only requests do not add payload transport. The check closes the ColorArray channel axis without adding another closure over `atomic_trailing_axes`; an incomplete tuple fails as `Protocol/Group` before any member reply is committed.

The phase lends one limited workspace allocator and a shared Run/root work charge. Each member ResourceBudget must be the continuation Root; phase and member allocators must share its nonempty accounting domain. The host verifies Root ownership of outcome and nested Need storage before use. A contract-2 quality report must belong to the member ResourceBudget and phase resources, and be owned by the phase or shared workspace allocator. `BufferAllocator::same_owner` compares only accounting-domain identity, not quotas or provenance, and grants no payload access. The callback exception fence preserves the first shared allocation, work, or I/O failure. C++ Result factories and polls map `std::bad_alloc` to `ResourceExhausted`, standard exceptions to `OperationFailed` with `HostException` and their diagnostic (empty when `what()` is null), and non-standard exceptions to `OperationFailed` with a fixed `HostException` diagnostic. A recorded phase failure takes precedence over a subsequent throw, and an exception from the host failure observer cannot replace the producer's selected failure. Later polls return a latched group failure; concurrent or reentrant polls are rejected without replacing the active poll's result.

For contract 2, an Atom failure names its exact `AtomKey`. A `ValidationDomain` failure must have Domain or Schema origin and match the output's complete fixed observation domain, not the current query subset. The host applies it to matching Ready and Waiting members in the continuation and rejects a later domain failure that would revoke a semantic-terminal member. Contract-2 outcomes may carry a `QualityReport`; success evidence is checked against the published Float64 estimate, while Measured evidence may accompany a matching Domain failure. See [Atom errors and quality](Atom-Errors-and-Quality.md) for the complete evidence contract. The quality report's snapshot label is independent of the routing `snapshot_identity`.

Structured execution groups eligible, ready CPU Result queries from the same node through contract 1 or contract 2. Contract 2 admits up to 64 one-observation queries, including distinct Q values for the same output; it does not split a query spanning several observations into atoms. Completed, cached, pruned or otherwise ineligible Actors stay out of a shared start. Disabling C1 grouping leaves contract 1 on its singleton path, while contract 2 still uses its required one-member joint callback. The coordinator invokes the shared start, fulfills each member's Needs and submits later rounds as members become ready. It validates the full round before publishing any result. Contract-1 fallback is limited to failures accepted by its optional unscoped-error predicate, including eligible backend or admission failures; cancellation, stale, protocol, domain/schema and Run-scoped failures are not retried. Contract-2 group, protocol and Run failures are terminal and never fall back to singleton callbacks.

For contract 2, the Run ledger keys ValidationDomain failures and semantic-terminal observations by compiled producer semantic identity, output and tensor slot. Semantic aliases of one compiled producer share finality; failure details continue to identify the actual workflow node. Each output uses one tensor slot within a cohort, while a conflicting slot is handled by a later cohort. The ledger spans cohorts, completed-cache reuse and Actor retirement. A domain failure applies to matching Ready and Waiting members, and a later failure cannot revoke an earlier terminal observation. The coordinator allocates each query's payload-free failure and quality record before callbacks, so terminal recording does not allocate. Completed or terminal contract-2 Actors remain registered until the first delivery consumes them; contract 1 keeps its existing weak-completion policy. Shared producer entries carry attached quality with their publication or failure. Domain failure identity and evidence continue downstream; successful transformations do not inherit input quality. Quality-bearing results are skipped by completed-output content retention. `ExecutionContext::execute_atoms` uses the structured coordinator to collect the named Result observations and their scoped dependency roots. Structured Result joint execution is CPU-only.

The C Result ABI 2 output record declares `observation_kind` and `failure_delivery`. Its optional CPU `joint` program supports contract 1 and contract 2; the operation still provides singleton callbacks. Contract 1 requires at least two Atomic outputs with RequestFailureOnly delivery and groups 2..64 distinct output indices. Contract 2 requires Atomic outputs with PerAtomOutcome delivery and accepts 1..64 distinct full `AtomKey` members through the direct registry entry point or structured CPU workflow. Different observation coordinates may name the same output, but they use its one fixed tensor slot. The importer requires the current full program and nested structure sizes.

For either contract, the start callback receives the active non-cancelled query subset, which may contain one member, and no payload-read service. The host creates one zeroed state payload and calls `destroy` exactly once after start is entered, including on start failure. Each `poll` receives ready members with per-member Result services and shared scratch/work services; its active subset may also contain one member. The outcome array must contain each full AtomKey exactly once. Contract 1 additionally requires distinct output indices and permits an ordinary C error as a member result. Contract 2 requires `PS_RESULT_ATOM_FAILURE_V2` for a typed member failure; a nonzero poll callback return fails the entire group. Host service errors such as cancellation and resource exhaustion retain their host status and failure detail. The host checks the whole array before translating outcomes and applies the common Result schema, scope, Root, completeness, and exact-query validation. Scratch retires at poll return, work is charged to the Run and Root, and the shared handle source prevents cross-member handle collisions.

Contract-2 failure records copy the error code, reason, origin, scope, and a diagnostic of at most 4096 bytes. Scope is limited to the exact Atom or a fixed ValidationDomain with Domain or Schema origin. The callback cannot provide producer node/input identity; the host derives it from the actual producer. The shared poll services also create Measured or IntegerDiagonal quality reports. Their opaque handles are valid for that callback epoch and can be attached to successful publications or Domain-origin Atom/ValidationDomain failures carrying Measured evidence, for members in the same poll. They are distinct from member-service handles and cannot be reused across joint groups. A callback may create a report during a poll that returns Need, but the Need outcome's quality field must be zero; unused reports retire with the callback lease. The host takes an owning copy of attached reports before the lease retires, then delegates Result evidence validation to the continuation, which checks successful evidence against the published Float64 estimate. Contract 1 does not carry quality. The C singleton operation table has no typed Atom failure or quality attachment.

`test_result_c_joint.cpp` covers contract-1 members with different output shapes: the left output has shape `{1}`, the right has shape `{2}`, and requesting right coordinate `1` returns `11` while coordinate `0` remains unreadable. Disabling joint grouping uses the singleton callbacks and preserves the same value and per-output dirty results. `c_joint_payload_bounds()` additionally checks contract-2 members with output-specific payload caps: a zero-byte cap fails only the left member with `CapacityLimit`, while the right member's eight-byte cap permits value `11`, with grouping both enabled and disabled. `wide_sparse_output` in the same test uses a Float64 domain of size `2^61`, reads only the first and last points through an 8-byte window under a 64 KiB Payload limit, and checks Root cleanup. It validates sparse endpoint access, not dense allocation or wide-domain GPU execution.

Adding `joint` changes the binary layout of `ps_result_operation_v2`. ABI 2 requires the exact current `struct_size`; a prefix-sized older operation record is rejected, so C modules must be rebuilt. The C joint bridge is CPU-only. Contract 2 has no GPU joint backend. Joint callbacks are a grouped Result execution contract; singleton Result callbacks remain available for each declared output.

## Ready Atomic execution groups

`ExecutionPlan::execution_groups()` lists optional CPU contract-1 alternatives for retained singleton steps. `ExecutionOptions::enable_joint` disables this C1 grouping optimization. Contract 2 remains a joint protocol and uses its required one-member callback when grouping is disabled. The coordinator registers requested roots and declared input demands, then groups only observations already known and ready; it does not wait for future requests or combine different Runs.

When any structured Result consumer returns a validated Need, the coordinator pre-registers its eligible computed CPU contract-1 inputs before reading upstream. It closes and unions tensor footprints by input port and slot, charges sorting and registration work to the Run, and records the selected C1 producer steps in a short Root-owned scope. While that scope is active, only matching C1 actors and their aliases are deferred, allowing the full input-demand batch to be installed before those callbacks start; unrelated peers may advance. C2 producer inputs are not preregistered through this path, and cache replay does not register new demands. Actor setup can still prepare scalar inputs or reuse cached Results while an individual demand is installed, so a later admission failure does not undo completed preparation. The low-Root-work case in `test_joint_execution` has no scalar preparation and verifies that the consumer's first poll is followed by `ResourceExhausted` before the C1 producer callback runs.

The coordinator registers explicitly requested named Result roots before advancing Actors. Potential CPU contract-1 joint candidate roots can remain deferred until their consuming Actor validates its Need and registers the relevant producer inputs; this gives peer C1 inputs a chance to join before those candidates start. The Root-owned pending-task list retains each queued or submitted Actor until dispatch rejection or callback retirement. Once the dependency frontier has queued work, the coordinator submits at most `maximum_parallelism` callbacks, waits for the submitted wave to retire, then applies phase results serially before advancing the next frontier. CPU staged-tile coordination and GPU dispatch keep their existing paths.

Before a producer serves a Need, the coordinator validates the complete Need envelope. Each input keeps an independent supply cursor, and the coordinator rotates among inputs that can progress. It visits each Actor at most once per traversal, avoiding repeated recursive walks through deep chains as peers wait on upstream producers. Stage-local transfer, tile and native observations remain attached to their submitted task and merge when the driver retires it. A joint worker marks entry and executes the callback; the driver accounts for the group once at retirement. Checkpoint and block-cache metadata locks protect bounded lookup or commit sections, not their computation or test hooks.

`JointScope` bounds nested joint input evaluation to 16 levels; deeper work continues through ordinary Actor progression. A scope restores its active joint, cancellation and failure route after each step, including host Metadata allocation failure. Identical ready input sets share transport while each member keeps its own source records and role associations. Shutdown and synchronous Run completion drain every submitted task before borrowed callback state is released.

During Result joint Need preflight, a member-local `Cancelled` or `Stale` status ends only that member when it is neither Protocol-origin nor Run/Group-scoped; eligible peers continue. Protocol-origin errors and any Run- or Group-scoped failure remain enclosing failures and terminate the joint round.

Whole-result release remains conservative. Only a completed, non-contract-2 Whole Actor whose every tensor slot has full coverage can mark its aliased steps finished. Liveness counts only steps reachable from requested roots and follows each step's selected `input_indices`. The coordinator clears the published object and producer lease only after all aliases have no remaining consumers or named-output pin and no pending or joint work. A Dynamic Dependency, Prefix, Empty, or C2 publication cannot mark a step complete from one partial publication. Published Results and retained read windows keep their own storage owners independently. Poll timing spans phase creation through driver retirement, including callback queue and wave wait; it is not a compute-only measure.

`test_result_dag_parallel` exercises the callback wave limit and cancellation, keeps source backing alive while the independent left/right consumers read it, then checks that the source owner expires before the join publishes. Its named-output case runs the left and right producers concurrently and returns their separately owned Results; its single-output case keeps the final value `7` readable through an escaped `ResultRef` after context teardown, with eight Payload bytes retained until that reference is released. A held-output admission failure releases its resources and a later Run recovers. `test_joint_execution` checks two gated C1 producer factories joining independently and queue-admission failure with no callback entry.

Each observation claims its own shared producer entry and content proof. The coordinator skips optional sibling claims that exceed admission and separately subscribes to work owned by another Run. Cache hits do not join computation. Successful members publish their evidence, flights and eligible cache entries independently; local errors remain attached to their own results. Completed sibling values remain accounted until their registered consumer takes them. Shared backing uses its existing storage domain and unique-owner accounting, and fallback ancestry disables caching only for the affected member.

A Result joint group reserves shared continuation state and host member adapters once. Each poll admits ready members' output and workspace, actual supplied-input multipliers and shared scratch; joint work consumes the remaining Run budget. Contract 1 can fall back to singleton execution only after a failure accepted by its optional unscoped-error predicate, releasing group resources first. Contract-2 group, protocol and Run failures are terminal and do not fall back. Cancellation and invalidation also do not retry. The coordinator refreshes member leases during upstream work, and a cancelled original requester does not cancel another Run's active waiter.

`test_joint_execution` covers root and consumer-driven Result grouping, independent projections, shared owner windows, sum `18`, 64-deep dependency chains, admission and fallback, cancellation and GPU-fallback ancestry. Its `maximum_result_checkpoint_scopes=1` case still admits a Result joint group because that configuration bounds checkpoint scopes rather than shared-producer entries. A separate 1 GiB shared-continuation case covers contract-1 fallback after group admission fails. The consumer-driven case checks registration of two computed C1 outputs from one singleton Need. `test_dependency_joint` covers 64 Result contract-1 members with different output shapes, nonzero first/middle/last coordinates, cancellation and callback suppression after a pre-failure. `test_atom_outcomes` tests Result domain failures across 65 observations and a dependency DAG. `joint_groups`, `joint_polls` and `joint_fallbacks` report the physical path actually taken.

### Compact static dependency mappings

`DependencyCertificate::create_mapped` stores disjoint coverage pieces and port/role axis maps as immutable metadata. Each input axis selects an observation axis or fixed interval; tags remain explicit. This representation supports exact broadcast/permutation projection and dirty transpose without enumerating replicated samples. Restriction and equal-map merge remain geometric; different maps on overlapping coverage may require bounded row comparison. `row` resolves one observation, `materialize` explicitly requests bounded rows, and `rows()` throws for mapped certificates. Transformations charge work and retained metadata, including canonical box expansion. `storage_entries()` counts retained coordinates, supports and tags independently of a deduplicated source-support projection. A mapped certificate describes evidence; it does not define a staged callback protocol.

Structured Result tensor operations publish a `ResultRelation` over logical coordinates in the complete sample shape, including batch axes before cell axes. Tensor description facets participate in declared metadata and validation support; physical layout does not invent dependencies.

### Cross-output pure block sharing

`share_blocks_across_outputs` is an optional `OperationTraits` v25 field for pure deterministic Atomic Result operations. It is disabled by default. When enabled, the runtime may retain compatible block state transitions across outputs; incompatible state or denied retention causes recomputation. Block retention remains separate from complete Result caching, checkpoints and published outputs. Hit counts and reuse scope are implementation details, not performance guarantees.

## Limits and failure handling

Exact-set construction, certificate growth, Result discovery, callback stages and retained demand metadata have separate finite limits. Invalid domains or protocol envelopes fail as errors; limit exhaustion returns `ResourceExhausted`; cancellation returns `Cancelled`. The caller must retain the bundle or owners for borrowed inputs through each call and should retry only statuses documented as retryable by the owning execution API.
