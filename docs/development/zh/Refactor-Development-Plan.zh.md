以上候选没有分配 GitHub 编号。开放标题清单和选定的详细正文没有显示匹配的 C++20 或结果缓存、RT 请求或磁盘缓存的专门实现任务；这是有界搜索，无法证明所有旧讨论都没有重叠。创建任务前检查候选匹配。本文件记录交付范围，不构成第二份任务状态跟踪。S3 至 S5 在相邻接口和决策准备就绪前仍属于结果级规划。

对于标量输入，保守的 Whole 算子可以作为第一步实现：它读取完整图像和完整的rank-1 标量。也可以制定明确的逐端口规则，仅对图像端口使用 Elementwise/Halo，对标量端口使用 Whole。两种选择都必须发布标量类型、形状、有限值与值域验证和失败处理责任；两者都不会自动遵循当前 PreserveFirstInput 规则。建议的 #256 修订为逐端口契约及其 ABI 后果准备评审材料。向精确大小的 C 描述符增加字段需要明确的新 ABI 布局/版本；只有在新宿主拒绝发送 Float32 值给缺少该能力的旧插件时，独立的能力标记方案才可以保留 v2 布局。单纯增加枚举或建议重新编译都不足够。现有 Elementwise/Halo 语义保持不变。

## 需要后续决策的条款

- S2：为实际部分物化修订 Value/Region/算子输出和 Storage ownership。保持逻辑语义、物理布局和存储分离；在预算中明确输入源和输出端的内存。
- S3-A：将正向失效传播和结果缓存所有权与反向输入需求和编译缓存身份分开引入。HP 表示正式的全质量派生结果；RT 表示临时 previews。这些是提议迁移的语义，当前没有已实现的缓存服务。
- S3-B：区分冻结导出快照的生命周期、最新预览发布和共享缓存工作生命周期。保留过期检查，等待该决策完成。
- S3-C：提议有限替换与 ADR 0015 冲突的条款，用于可丢弃并重建的本地磁盘派生数据。排除工作状态持久化、恢复、用户文档保存、持久输出权威和远程存储。明确选择所有者；旧 GraphCacheService 代码仅作历史参考。
- S4：定义进程内跨 Run 驻留的所有者、有效性和预算，并在资源复用前等待设备完成事件。单独的 shared_ptr 生命周期不定义异步原生设备工作的完成。
- 工具链/框架：C++20 需要明确的工具链/消费者选择；完整的 MLIR/Halide 采用需要有界的比较实验。内部 IR 的稳定序列化仍在当前边界之外。
